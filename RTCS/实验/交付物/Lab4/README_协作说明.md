## 2. Task 1 怎么做（25 分）

### 2.1 要做出来的现象

串口上出现三个任务轮流打印的计数，像这样：

```
Task 3: counter = 69
Task 1: counter = 70
Task 2: counter = 71
Task 3: counter = 72
```

**判断做对了没有，只看一件事：计数必须每行加一，不跳号也不重复。**
跳号或重复就说明有自增被丢了或被覆盖了——那正是互斥量要防的事。

### 2.2 结构

三个任务的代码是**完全一样**的，只有"我是几号"和"开机时先等多久"两个参数不同。所以写成一个公共函数、三个入口各调一次就行，不要复制三遍（复制三遍最容易出现改了一处忘了另两处）。

每个任务的循环就四步：

```
拿锁（拿不到就等） → 自增 + 格式化 + 发串口 → 放锁 → osDelay(750)
```

**开机错峰**：三个任务分别先 `osDelay` 0 / 250 / 500 ms 再进循环。三个任务周期都是 750 ms、彼此错开 250 ms，稳态下每 250 ms 正好有一个任务来拿锁，锁基本不冲突，输出干净。

> 错峰只是让**输出好看**，**正确性仍然是互斥量保证的**——报告里这两件事要分开说，别把"轮转整齐"当成"互斥量生效"的证据。

### 2.3 三个必须这么写的地方

| # | 怎么写 | 为什么不能用另一种写法 |
| --- | --- | --- |
| **1** | `osMutexAcquire(myMutex01Handle, osWaitForever)` | **手册给的示例用的是超时 0**，拿不到锁就跳过这次自增（手册原话是 "it simply skips"）。那等于**悄悄丢掉一次自增**——正是互斥量要防的事，换个方式又发生了一遍。等待不花钱：阻塞的任务不在就绪队列里，不占 CPU |
| **2** | 串口发送**放在持锁区间内** | 这是个取舍。持锁期间做阻塞发送（115200 下一行约 2 ms）确实不够理想，但**好处是计数值和打印它的那一行绑死**：若自增完就放锁，另一个任务可能抢在前面打印，输出顺序就乱了，而计数本身并没错。这道题的证据就是输出，所以选了顺序。**报告里把这个取舍写清楚是加分项** |
| **3** | `osDelay(750)` 放在**放锁之后** | 持锁期间睡 750 ms 会把另外两个任务锁死整整 750 ms，这题就没得看了 |

参考实现在 `代码/Task1_mutex_three_tasks.c`，按 `USER CODE` 分区标好了每段该贴哪。直接用或者照着写都行。

## 3. Task 2（25 分）——不需要你

Task 2 是写作题：**信号量与互斥量的主要区别，以及一个互斥量做不到而信号量能做的用例。** 没有代码、没有硬件。这部分我这边写完了，答案要点是：

- **根子上的区别是"有没有属主"**：互斥量记录是哪个任务拿的，信号量只是个计数。其余区别——谁能释放、能放几个进去、能不能做优先级继承——全都是从这一条推出来的。
- **互斥量做不到的典型用例是"中断里给任务发信号"**：互斥量只能由属主释放，而中断不是任务、没有可阻塞的身份，`osMutexAcquire` 在中断上下文里直接返回 `osErrorISR`。信号量没有属主，中断里可以直接 release。
- 次要的一个用例是**限制同时访问的任务数**（比如三条 DMA 通道、十个任务要用），计数信号量天然表达得了，互斥量只能放一个进去。

**顺带一提**：手册自己的信号量示例用的是 max = 2 的计数信号量，并说它"控制对共享资源的访问"——但 max = 2 意味着**允许两个任务同时进临界区**，共享的 `buff` 其实还是竞态的。这不算手册写错（信号量本来就是限并发不是互斥），但容易被读成"信号量能保护共享数据"。报告里我把这点写进附录了。

## 4. 必踩的坑（按"会不会让你直接跑不起来"排序）

| # | 坑 | 症状 | 处理 |
| --- | --- | --- | --- |
| **1** | **HAL 时基没从 SysTick 换到 TIM4** | 板子完全没反应，或进 `HardFault` | §1 第 2 步，⚠ 必须 |
| **2** | **`TOTAL_HEAP_SIZE` 还是默认的 3072** | **某个任务从头到尾一声不吭**，别的任务正常（`osThreadNew()` 返回了 `NULL`） | 改成 **8192**，并在 `MX_FREERTOS_Init()` 末尾检查互斥量和三个任务句柄是否为 `NULL` |
| **3** | **用了手册示例的 `osMutexAcquire(handle, 0)`** | 计数跳号——两个任务抢锁时有一次自增被跳过了 | 改成 **`osWaitForever`**，见 §2.3 第 1 条 |
| **4** | **`osDelay` 写在持锁区间里** | 只有一个任务在打印，另外两个几乎不出现 | 放到 `osMutexRelease` 之后 |
| **5** | 出错路径上忘了放锁 | 跑一阵后全部卡死 | 任何提前 `return` / `break` 之前都要先 `osMutexRelease`。参考实现的做法是**不提前返回**，统一走到释放那一行 |
| **6** | 用 `printf` 打印 | 栈瞬间吃掉几百字节，连带触发坑 2 | 用 `snprintf` 到小缓冲区再 `HAL_UART_Transmit` |
| **7** | 三个任务给了不同优先级 | 高优先级那个刷屏，看不出轮转 | 三个都给 `osPriorityNormal`，见 §0.3 |
| **8** | `snprintf` 的返回值没检查 | 缓冲区不够时发出截断的乱行 | 检查返回值在 `0 < length < sizeof buf` 之间 |

## 6. 常见报错对照

| 现象 | 多半是 |
| --- | --- |
| 编译报 `osMutexAcquire` / `osMutexRelease` 未定义 | FREERTOS 的 Interface 选成了 CMSIS_V1，改回 **CMSIS_V2** |
| 找不到 `myMutex01Handle` | Mutexes 页没建，或者建完没重新 Generate Code |
| 下载进去完全没反应，调试器停在 `HardFault_Handler` | 坑 1（时基）或坑 6（`printf` 爆栈） |
| 只有一两个任务在打印，第三个从没出现过 | 坑 2，堆不够，第三个任务压根没创建成功 |
| 计数偶尔跳号（70 → 72） | 坑 3，用了超时 0 的 `osMutexAcquire` |
| 计数出现重复（两行都是 70） | 锁根本没生效——检查是不是漏了 `osMutexAcquire`，或者三个任务用的不是同一个句柄 |
| 串口全是乱码 | 波特率不一致，核对串口助手和 CubeMX 里都是 115200 |
