### 0.4 两个大题的任务与优先级

**Task 1（35 分）**——手册要求两个任务，一个管刹车、一个管串口消息：

| 任务 | 名字 | 优先级 | 栈 | 干什么 |
| --- | --- | --- | --- | --- |
| 刹车 | `task_brake` | **osPriorityAboveNormal**（高） | 128 words 默认即可 | 按键按下 → 点亮 LD2 一段时间（刹车灯），并通知串口任务 |
| 消息 | `task_message` | **osPriorityNormal**（低） | 256 words | 收到通知 → 串口打印一条"正在减速" |

**⚠ 刹车必须是高的那个。** 手册给的情景就是答案：自动驾驶里"减速"比"点亮刹车灯提示"更要命，延迟这一项会出人命；打印一条消息晚几十毫秒没有任何后果。报告里这一问就按这个逻辑答——**按后果的严重性排，不是按代码量或执行时间排**。

**Task 2（65 分）**——两个任务、三个队列：

| 任务 | 名字 | 优先级 | 栈 | 干什么 |
| --- | --- | --- | --- | --- |
| 通信 | `task_comm` | **osPriorityNormal**（高） | 256 words | 中断收 11 个字符 → 原样回显 → 解析 DELAY → 投进队列 1；同时把队列 2、3 里的数打印出来 |
| 执行 | `task_led` | **osPriorityBelowNormal**（低） | ⚠ **256 words** | 按队列 1 给的速度翻转 LD2；每翻 10 次往队列 2 投一个递增数；每收到一次队列 1 的新值就生成 150 个随机数、把最大的投进队列 3 |

**这里为什么是通信任务更高**：两个任务绝大部分时间都阻塞在 `osDelay` 或队列上，优先级其实很少起作用；真正会起作用的是 `task_led` 填那个 150 元素数组的时候——那是一段**不阻塞的纯计算**。如果把它设成高优先级，这段计算会把串口打印顶住。LED 翻转容忍几毫秒抖动，串口要及时响应命令，所以**让执行任务低、通信任务高**。报告里可以就这么答。

### 0.5 这次要不要管时钟

**基本不用，但截图还是要。**

- `osDelay()` 的单位是 **RTOS tick**，CubeMX 默认 `configTICK_RATE_HZ = 1000`，也就是 1 tick = 1 ms，**和主频无关**。所以 Lab 1 那个"定时器时钟必须去时钟树上读"的坑，这次不踩。
- 但 **UART 波特率**和 **HAL 时基（TIM4）的分频**仍然由时钟树决定，CubeMX 会自己算好。
- ⚠ **还是请把 Clock Configuration 页面截一张图回传**——报告要写系统配置，而且万一波特率对不上（串口全是乱码）第一个要查的就是它。

## 1. CubeMX 六步配置

两个工程都一样，做完再分别加各自的任务和队列。

1. 新建工程 → **Board Selector** 选 **NUCLEO-F103RB** → 问你是否初始化全部外设，选 **Yes**（这样 PC13、PA5、USART2 一次配好）。
2. **System Core → SYS → Timebase Source 改成 TIM4**。⚠ 这一步最容易漏，漏了后面什么都不动。
3. **Middleware and Software Packs → FREERTOS → Interface 选 CMSIS_V2**。
4. **Connectivity → USART2 → NVIC Settings → 勾上 USART2 global interrupt**。
5. **FREERTOS → Config parameters → `TOTAL_HEAP_SIZE` 从 3072 改成 8192**。⚠ 不改的话任务可能根本创建不出来，见 §4 坑 4。
6. FREERTOS 的 **Tasks and Queues** 页，按 §0.4 的表加任务（和 Task 2 工程的队列，见 §3.2）。

> **改任务属性的地方**：双击任务那一行，弹窗里改 Task Name、Entry Function、Priority、**Stack Size**。手册 Figure 2b/2c 就是这个弹窗。

生成代码后，在 `main.c` 里找 `StartTask_xxx` 那几个函数模板，往里面的 `for(;;)` 填东西。**⚠ 只在 `/* USER CODE BEGIN */ … /* USER CODE END */` 之间写**，不然下次在 CubeMX 里改一下配置、重新生成，你写的全没了。

## 2. Task 1 怎么做（35 分）

### 2.1 要做出来的现象

按一下蓝色按键 → 板载 LED 亮起来一段时间（代表踩了刹车、刹车灯亮）→ 串口同时冒出一行消息说车正在减速 → LED 熄灭，等下一次按。

### 2.2 结构

```
按键 PC13 下降沿
      │  (EXTI 中断，里面只做消抖 + 投一个消息，不干活)
      ▼
   队列 brakeQ  ──►  task_brake（高）：点亮 LD2 → 往 msgQ 投一条 → 等 1.5 s → 熄灭
                          │
                          ▼
                      队列 msgQ  ──►  task_message（低）：串口打印一行
```

**为什么中断里只投消息、不直接点灯**：这是 RTOS 的通用纪律，也是 Lab 1 讲过的"ISR 要尽量短"。真正的理由在这次更明显——**点灯和打印都放进中断的话，这道题就没有"两个任务"可言了，优先级也就无从演示**。

**为什么用队列而不是一个全局变量**：手册 §4 图 7 专门讲了全局变量的坑。这里其实只传一个"有事件"的信号，用 `volatile` 标志也不会错；但**用队列的好处是低优先级任务可以 `osWaitForever` 地阻塞在上面，一点 CPU 都不占**——而标志位只能轮询。报告里这一句值得写。

### 2.3 消抖

机械按键一次按下会产生好几个边沿。沿用 Lab 1 的办法：**距上一次被接受的边沿不足 200 ms 的，直接丢弃**。在中断里用 `osKernelGetTickCount()` 取当前 tick 比较即可。

## 3. Task 2 怎么做（65 分）

### 3.1 字符位置对照表

手册说"第 2–6 个字符是 DELAY"、"第 8–11 个字符取成整数"，这是**从 1 开始数**的。写代码时是从 0 开始，差一位，这里列死，照着写不会错：

| 手册说的 | 例子 `-DELAY 1000` 里是 | C 里的下标 |
| --- | --- | --- |
| 第 1 个字符 | `-` | `buf[0]` |
| 第 2–6 个字符 | `DELAY` | `buf[1]` 到 `buf[5]` |
| 第 7 个字符 | 空格 | `buf[6]` |
| 第 8–11 个字符 | `1000` | `buf[7]` 到 `buf[10]` |
| 合计 | 11 个字符 | `buf[0..10]` |

判断是不是 DELAY 命令：`memcmp(&buf[1], "DELAY", 5) == 0`。
取数：把 `buf[7..10]` 四个 ASCII 数字转成整数，最大 `9999`，**正好能塞进 `uint16_t`**。

### 3.2 三个队列的宽度和深度

手册最后要求"描述每个队列的 size 和 width 并说明理由"，这是明确的采分点。定成这样：

| 队列 | 装什么 | 元素类型 | **width**（item size） | **size**（深度） | 理由 |
| --- | --- | --- | --- | --- | --- |
| **队列 1** | DELAY 命令给的毫秒数 | `uint16_t` | **2 字节** | **2** | 四位数字最大 9999，2 字节够。这是**命令**不是数据流——只有最新那个值有意义，队列开深了只会让 LED 追着过期的命令跑。留 2 格是为了容下一个"在途"的 |
| **队列 2** | 每翻转 10 次递增一次的计数 | `uint16_t` | **2 字节** | **8** | 产生频率是每 10 × delay 毫秒一个，delay 小的时候相当快；消费者（通信任务）可能正忙着打印，**留几格吸收抖动**，满了也只是丢一个计数、不影响主功能 |
| **队列 3** | 150 个随机数里的最大值 | `uint32_t` | ⚠ **4 字节** | **4** | **这一格最容易错**：`rand()` 的上限 `RAND_MAX` 在 STM32 的 newlib 里是 `0x7FFFFFFF`（约 21 亿），**远远超出 2 字节**。用 `uint16_t` 会把结果截断成垃圾。深度 4 是因为它只在收到 DELAY 命令时才产生一个，频率很低 |

**在 CubeMX 里怎么填**：Tasks and Queues 页 → Queues → Add，`Queue Size` 填上表的"深度"，`Item Size` 填"宽度"（手册 Figure 9 就是这个弹窗）。

### 3.3 那个 150 元素的数组——这是手册埋的考点

手册 §3 用 200 个整数讲过一遍，这里原样复现：

$$150 \text{ 个 int} \times 4 \text{ 字节} = 600 \text{ 字节}$$

而 CubeMX 给任务的**默认栈是 128 words = 128 × 4 = 512 字节**。600 > 512，**放不下**。

**症状**：程序跑起来，打印第一行之后就卡死 / 板子反复重启。和手册 §3 描述的一模一样。

**⚠ 改法：把 `task_led` 的 Stack Size 从 128 改成 256**（= 1024 字节）。留 400 多字节给其它局部变量和中断现场，是安全的。

> 为什么不填刚好够的 150：栈上除了这个数组还有循环变量、函数调用的返回地址、以及中断发生时压进去的现场。卡着 600 字节填必崩。**取 2 的幂且留足余量**是通行做法。

> [!warning] ⚠ 还有一笔更容易漏的账：这些栈是从同一个堆里出的
> 手册 Figure 6 那张 Config parameters 截图里有一行 **`TOTAL_HEAP_SIZE`，默认只有 3072 字节**（方案 `heap_4`）。
> **任务的栈、任务的 TCB、三个队列，还有你没写但一定存在的空闲任务和软件定时器服务任务，全都从这 3072 字节里出。**
> 本次两个任务都按 256 words 开，光栈就是 1024 × 2 = **2048 字节，三分之二没了**，再加上其余几样必然超。
> **症状和栈不够完全不同**：栈不够是任务能起来、跑一下才挂；堆不够是 **`osThreadNew()` 返回 `NULL`，那个任务从头到尾一声不吭**，别的任务却一切正常——极容易误判成逻辑写错了。
> **⚠ 两件事**：① 按 §0.2 第 4 行把 `TOTAL_HEAP_SIZE` 调到 **8192**（F103RB 有 20 KB SRAM，放得下）；② 在 `main.c` 里**检查 `osThreadNew()` 和 `osMessageQueueNew()` 的返回值**，为 `NULL` 时点个灯或打一行，别让它静默失败。

手册还提了另一条路：用 `malloc()` / `free()` 从堆上要内存（CMSIS-RTOS v2 下它们是线程安全的）。**○ 两种都可以，报告里建议两种都写，说明为什么选了扩栈**——扩栈是静态确定的，不会有内存泄漏和堆碎片，对实时系统更可预测；手册 §3 自己也说"严格禁止动态分配的场合用 heap 1"，方向是一致的。

### 3.4 UART 中断收 11 个字符

```
HAL_UART_Receive_IT(&huart2, rx_buf, 11)   ← 预约"收满 11 个字符叫我"
            │
            ▼  收满了，HAL 在中断里回调
HAL_UART_RxCpltCallback()   ← 只做两件事：把数据搬到第二个缓冲区、置一个标志
            │                  ⚠ 然后立刻再 arm 一次，否则只收得到第一帧
            ▼
      task_comm 看见标志 → 回显 → 解析 → 投队列 1
```

**⚠ 两个必须**：

1. **回调里必须重新 `HAL_UART_Receive_IT`**，否则收完第一帧就再也不响应了。
2. **回调里不要做打印和解析**。中断里调 `HAL_UART_Transmit` 会和任务里的打印撞车。

**为什么这里用"双缓冲 + volatile 标志"而不是第四个队列**：题目规定就是 3 个队列，不好再加。这里用标志是安全的，理由要写进报告——**只有一个写者（中断）、只有一个读者（任务）、标志本身是 1 个字节的原子写，而且数据是在置标志之前就拷完的**。手册 §4 图 7 讲的那两种竞态（写一半被打断、被另一个写者覆盖）在这个结构里都不成立。

> ○ 更地道的写法是用 CMSIS-RTOS v2 的**线程标志**（`osThreadFlagsSet` 可以在中断里调，任务用 `osThreadFlagsWait` 阻塞等）。这超出了本次手册的范围，**建议写进报告的讨论段，代码仍用双缓冲**。

### 3.5 要做出来的现象

- 串口发 `-DELAY 1000` → 立刻原样回显 `-DELAY 1000` → LED 改成每 1000 ms 翻一次。
- LED 每翻 10 次（也就是 10 秒后）→ 串口冒出一行队列 2 的计数：1、2、3……
- 每发一条 DELAY 命令 → 串口还会冒出一行队列 3 的数（150 个随机数里的最大值，是个很大的数）。
- 再发 `-DELAY 0200` → LED 变快，队列 2 的计数也跟着变快。

**演示建议 ○**：按 `-DELAY 1000` → `-DELAY 0200` → `-DELAY 2000` 这个顺序各发一次，录一段串口输出截图，三种速度的差别在计数的间隔上看得很清楚。

## 4. 必踩的坑（按"会不会让你直接跑不起来"排序）

| # | 坑 | 症状 | 处理 |
| --- | --- | --- | --- |
| **1** | **HAL 时基没从 SysTick 换到 TIM4** | 板子完全没反应，或者进 `HardFault` | §1 第 2 步，⚠ 必须 |
| **2** | **任务里用了 `HAL_Delay()`** | 整个系统卡住，只有一个任务在跑 | 一律换成 `osDelay()`。手册 §2 专门讲了这条 |
| **3** | **`task_led` 的栈还是默认 128** | 打印一行就挂 / 反复重启 | 改成 **256 words**，见 §3.3 |
| **4** | **`TOTAL_HEAP_SIZE` 还是默认的 3072** | **某个任务从头到尾一声不吭**，别的任务正常（`osThreadNew()` 返回了 `NULL`） | 改成 **8192**，并检查创建函数的返回值，见 §3.3 |
| 5 | 队列 3 的 item size 填了 2 字节 | 打印出来的最大值是个被截断的怪数 | 填 **4 字节**，见 §3.2 |
| 6 | UART 回调里忘了重新 arm | 只收得到第一条命令，之后就死了 | 见 §3.4 |
| 7 | 收到 `-DELAY 0000` | LED 任务空转，CPU 被吃光 | 把下限钳到 1 ms，或者直接忽略 0 |
| 8 | PC13 开了片内上拉/下拉 | 按键时灵时不灵 | 选 `NOPULL`，板上已有外部上拉 |
| 9 | 在中断里调 `osMessageQueuePut` 时 timeout 填了非 0 | 返回错误码，数据丢了 | **中断里 timeout 必须填 0** |
| 10 | 用 `printf` 打印 | 栈瞬间吃掉几百字节，连带触发坑 3 | 用 `sprintf` 到小缓冲区再 `HAL_UART_Transmit`，或者用参考代码里那个手写的整数转字符串 |

## 6. 常见报错对照

| 现象 | 多半是 |
| --- | --- |
| 编译报 `osDelay` / `osMessageQueuePut` 未定义 | FREERTOS 的 Interface 选成了 CMSIS_V1，改回 **CMSIS_V2** |
| 下载进去完全没反应，调试器停在 `HardFault_Handler` | 坑 1（时基）或坑 3（栈） |
| 某个任务像不存在一样，别的任务都正常 | 坑 4，堆不够、`osThreadNew()` 返回了 `NULL` |
| 只有一个任务在跑，另一个永远不动 | 高优先级那个任务里有死循环但没 `osDelay`，它一直不让出 CPU |
| 串口全是乱码 | 波特率不一致；核对串口助手和 CubeMX 里都是 115200 |
| 串口只收到第一条命令 | 坑 6，回调里忘了重新 arm |
| 队列 3 打印出来的数总是很小或很怪 | 坑 5，item size 填成 2 字节被截断了 |
| LED 根本不翻转 | 队列 1 一直是空的——先确认回显正常（说明 UART 收到了），再确认 `memcmp` 那一行的下标是 `buf[1]` 不是 `buf[2]` |
