# L04 操作系统概述

> [!info] 这一讲的骨架
> 这一讲只讲一件事：**操作系统是一层精心维持的假象——它让每个程序都以为自己独占一整台机器。**
> 程序以为自己有一颗专属 CPU、一整块连续内存、一个叫"文件"的东西可以读写；实际上 CPU 只有一颗、内存要分给几十个程序、磁盘上只有磁头、柱面和扇区。
> 整讲就是这个假象怎么搭起来（抽象与资源管理）、用什么单位维持（进程与 PCB）、切换假象要付多少代价（上下文切换），以及**实时系统为什么必须把假象拆开一部分看**（RTOS 与超级循环之争）。
> 考试上这一讲没有直接对应的大题，但它是 Q4 调度那 25 分的地基：进程状态、就绪队列、上下文切换开销，到 L19–L20 画调度时间线时全要用。看懂即可，不必死记条目。
> 课程总览见 [[00 课程信息与考情]]。对应课件 `L04H_Overview-of-an-OS_2026-2027`，51 页。

## 1 操作系统是什么

**操作系统**（operating system, OS）是**管理其他所有程序的那个程序**。被它管的那些叫**应用程序**（application）。

两者之间靠一套约定好的入口打交道，这套入口叫**应用程序接口**（application programming interface, API）——应用程序通过 API 向操作系统**请求服务**，而不是自己去碰硬件。人则通过**用户界面**（user interface）直接和操作系统打交道，可以是命令行，也可以是图形界面（graphical user interface, GUI）。

课件把它的职责列成六条，可以归成三组：

| 它在做什么 | 课件的说法 |
| --- | --- |
| **当界面** | 在用户与硬件之间提供一个界面——一套"环境架构"；让使用变得方便，把繁琐的部分藏起来 |
| **管资源** | 让使用变得高效：支持并行活动、避免空转的周期；给每个用户分一份资源 |
| **做管制** | 提供信息保护；充当控制程序 |

"把繁琐的部分藏起来"和"给每个用户分一份"正是开头那个假象的两面：**抽象**让硬件看起来简单，**资源管理**让有限的硬件看起来够用。后面每一节都挂在这两条上。

## 2 这层假象是被逼出来的

操作系统不是设计出来的，是一步步被逼出来的。按课件的顺序，每一步都在解决上一步暴露的问题：

| 阶段 | 怎么用机器 | 被什么逼着往下走 |
| --- | --- | --- |
| **没有操作系统** | 人扳开关把程序手动送进去，靠面板上的指示灯看状态，用纸质登记表排队 | 单个用户要从头到尾自己安排一切 |
| **专职操作员** | 程序打在穿孔卡片上，交给操作员，他跑完把结果还给你；有了标准卡片库 | 人工交接慢，机器大量时间在等人 |
| **批处理系统**（batch） | 一个常驻内存的**监控程序**（monitor）接连处理一批作业，中途不需要用户介入 | 作业一旦卡在 I/O，整台机器就空等 |
| **多道程序设计**（multiprogramming） | 一个程序被 I/O 卡住时，CPU 转去跑另一个 | 换来了利用率，但操作系统必须学会同时管好多份内存、并在阻塞时挑出下一个任务——复杂度陡增 |
| **分时系统**（time sharing） | 用户也想实时和机器交互，于是把时间切成片轮流分给各个终端 | 交互需求 |
| **个人计算机** | 一人一机 | —— |

值得记住的是**多道程序设计那一行的因果**：它的全部动机是"**缩短 CPU 被 I/O 阻塞的时间，从而提高利用率**"。这和 [[L01 实时系统#8 CPU 利用率|L01 讲的 CPU 利用率]]是同一个量——那里是在问"留多少余量才安全"，这里是在问"怎么把余量填上"。

## 3 抽象：操作系统在给硬件铺管道

课件的说法是 **OS does the plumbing**——操作系统替你铺管道，你只管开关水龙头。

硬件是**具体而琐碎**的：操作它不仅要会编程，还得懂这块硬件本身。有了操作系统，用户和程序员不必关心管道怎么走，拧开龙头就行，于是生产效率更高。

### 3.1 一个例子：把数据写到磁盘

这个例子把"抽象"这件抽象的事说清楚了。不借助操作系统，往磁盘写一次数据要分三步，每步都要你懂磁盘的物理构造：

```text
Read(DataMemAddr, Size, DeviceId);        // 把数据从内存送到设备缓冲区
Locate(DeviceId, PlatterId, TrackId);     // 把磁头移到对的盘面、对的磁道
Write(DeviceId, Cluster);                 // 最后写进那个簇
```

操作系统把这三步打包成一个 `Write`，并且**用逻辑地址替掉物理地址**——你不再需要知道数据落在第几个盘面第几条磁道：

```text
Write(DataMemAddr, Size, DeviceId, LogAddr);
```

再往上还能更抽象：把内存和磁盘都当成"文件存储"，用一个统一的文件标识，然后调 C 标准库：

```text
fprintf(FileId, "%d", datum);
```

到这一层，"磁盘"这个词已经从代码里消失了。这就是 Unix 那句 **"Everything is a file"（一切皆文件）** 的意思。

### 3.2 三种视角，三套词汇

同一台机器，站在不同位置看见的是完全不同的东西：

| 谁 | 他眼里的操作 |
| --- | --- |
| 用户 | 复制、粘贴、发送、保存…… |
| 应用开发者 | `malloc()`、`fork()`、`open()`…… |
| 操作系统程序员 | 读磁盘、启动打印机、追踪鼠标…… |

三者串成一条链：**用户应用 —（服务请求）→ 操作系统 —（硬件指令）→ 硬件**。

课件在这里引了一句常被当作玩笑的话：**"计算机科学里的所有问题，都可以靠再加一层抽象来解决。"** 它在这一讲是字面意思——上面那三层，每一层都只跟相邻的一层说话。

## 4 资源管理：时间复用与空间复用

操作系统的另一个身份是**资源管理者**（resource manager）。硬件资源**永远是有限的**，问题是怎么把有限的资源用好、用满。

课件给的手段只有两个词，但它们概括了全部做法：

- **时间复用**（time-multiplexing）：同一份资源，不同的程序**轮流**用。CPU 就是这么分的——每个进程拿一段时间片。
- **空间复用**（space-multiplexing）：同一份资源，**切成块**同时分给不同的程序。内存就是这么分的。

除了分配，它还要**管住**用户程序和 I/O 设备的执行，防止出错和滥用——这就是第 1 节说的"控制程序"。

## 5 操作系统由哪些部件组成

课件列的部件清单：

| 部件 | 管什么 |
| --- | --- |
| **进程管理** | 怎么把一个程序跑起来？资源怎么分？ |
| **内存管理** | 内存分配、保护、虚拟内存 |
| **文件系统** | 二级存储 |
| **输入输出** | 设备驱动 |
| **网络** | —— |
| **安全** | —— |
| **图形界面** | —— |

前三个在课件里各展开了一页，是这一讲的重点。

### 5.1 进程

操作系统面对的各种活动或子程序统称**进程**（process）。课件给的要点：

- 用户应用和系统应用都算；
- 它被抽象成"进程"这个东西，**把全部执行上下文包在里面**；
- 它是**一个正在运行的程序的实例**——所以同一个程序**可以同时有多个进程在跑**（比如开两个一模一样的编辑器窗口）；
- **每个进程有独立的内存空间**；
- 操作系统负责创建和销毁进程、按截止期/优先级/先后次序**调度**它们、维持进程之间的**通信**与**并发**。

"实例"这个词是理解进程的钥匙：程序是躺在磁盘上的那堆指令，**进程是这堆指令加上它此刻的执行现场**。后面 [[#8 进程：这层假象的基本单位|§8]] 会把"执行现场"具体拆开。

### 5.2 内存

内存这一侧要回答的是"**怎么组织各个进程的内存**"：程序本身和数据都存在内存里；要支持多道程序设计；进程之间有时要共享数据；用**页**（page）来组织；还有**虚拟内存**（virtual memory）——**把二级存储也当内存用，而把 RAM 当成它的缓存**。

最后这句话值得停一下：虚拟内存的思路是把速度层级整个翻转过来看——不是"内存不够了去借硬盘"，而是"地址空间本来就在硬盘上，RAM 只是它的快取层"。

### 5.3 文件与 I/O

**文件**（file）是对"一大堆信息"的抽象，落在二级存储上，支持创建、删除、复制、粘贴这些标准操作，再往上还有搜索、备份等等。

**I/O** 则如 [[#3.1 一个例子：把数据写到磁盘|§3.1]] 那个例子所示：它需要设备专属的知识，所以操作系统用**设备驱动**（device driver）把这些知识关起来，对上只暴露一套标准接口。

## 6 内核怎么组织：单体与微内核

部件有了，接下来是软件工程问题：这些部件该怎么拼在一起？课件说这**不直观**，并列出四个互相拉扯的目标——**可靠性、向后兼容、可扩展、可移植**。两种经典答案分别偏向其中不同的几个。

![[L04 单体内核与微内核.png]]

**单体内核**（monolithic）是传统做法：**一个程序装下全部内核代码**，提供所有操作系统服务，应用通过**系统调用**（system call）进去。

- 好处：**快，效率高**——部件之间就是普通函数调用。
- 坏处：**可移植性差、难维护**；而且**一个小 bug 就能让整个系统崩溃**，因为所有代码都跑在同一个特权空间里。
- 代表：Unix 和类 Unix 系统；Linux 用可加载模块做了缓和。

**微内核**（microkernel）把内核缩到最小：内核本身只做"特权模式才能做的事"，其余功能搬出去做成**服务器**（server）——它们可能有特权，但通常没有。

- 好处：**开发快、好做单元测试、易维护**——改一个服务器不牵动别人。
- 坏处：**内存占用大**；**上下文切换和进程间通信太频繁**，这正是它的性能税；**不好实现**。

两者放在一起：**单体内核总体性能更好，微内核模块性与可扩展性更好，而在模式之间来回切换的代价很高。** 所以现代（多数商用）系统走**混合路线**：内核尽量小，但大多数服务器仍然留在特权的内核空间里——Windows NT 和 macOS 的 XNU 都是这么做的。

## 7 操作系统有哪几类，以及实时系统特殊在哪

课件分了三类，前两类略讲，第三类是本课程的主角。

**网络操作系统**（network OS）：面向计算机网络，方便文件共享与硬件访问，典型场景是企业里的局域网；比单机系统多的主要是通信功能。路由器上跑的 Cisco IOS 属于这一类。对等（peer-to-peer）结构下还要看网络拓扑。

**分布式操作系统**（distributed OS）：每个节点上放一份"微内核 + 协调用的服务组件"，各节点**合起来**才凑成一个完整的操作系统。单个节点能访问全系统的资源，代价是调度与并行变得复杂；用户通常**不知道**程序实际在哪个节点上跑、文件物理上存在哪——这些全由系统自动处理。

**实时操作系统**（real-time OS, RTOS）：专门用来满足**特定的时间约束**。它分两种，和 [[L01 实时系统#5 硬实时、固实时、软实时|L01 讲的硬实时与软实时]]是同一套划分——**硬实时**确保关键任务按时完成，**软实时**即使错过截止期，把任务做完仍然有价值。工业场景如机器人、飞行控制。

它的四条关键设计要求值得单独记，因为它们解释了"实时"这两个字到底要求了什么：

1. **可预测性与确定性**（predictability and determinism）——排在第一位；
2. **速度**：实践中当然重要，通常靠**简化操作系统设计**换来，而且**有时要拿可预测性和确定性去换**；
3. **响应性与用户控制**：把对的事做得**足够快**，而且优先级可以由用户动态调整；
4. **故障安全**（fail-safety）：出事时"直接全部关掉"未必是好选项。

此外它**要求更高级的调度与内存分配**——这正是 L19–L20 要讲的东西。

> [!warning] 第 2 条是这一讲最反直觉的地方
> 日常语境里"实时"几乎等于"快"。但课件把**可预测性和确定性排在速度前面**，而且明说速度有时要拿它们去换。
> 原因在 [[L01 实时系统#4 实时系统的定义|实时系统的定义]]里：正确与否取决于**结果有没有在截止期前交出来**。一台平均很快但偶尔抖动的机器，赶不上最坏情况下的那条线；一台平均慢一点但每次都稳的机器反而合格。
> 答题时若问"RTOS 和普通 OS 的区别"，这一条是拿分点，别答成"RTOS 更快"。

### 7.1 嵌入式操作系统

**嵌入式操作系统**（embedded OS, EOS）和 RTOS **严格说不是一回事，但大多数 EOS 都是 RTOS**、都以满足同样的时间约束为目标，所以**本课程里两个词可以互换使用**。

它的要点仍然围绕可预测性与确定性：主流调度算法都**基于对执行时间上界的预测**；中断是另一个关键。"实时"还要求对截止期有**统一的理解**、以及精确的时间服务（TAI 国际原子时、UTC 协调世界时）。为了快，**所有东西都坐在实时内核上，连设备驱动也是**。

反过来，什么可以不重要？**图形界面**大概率不需要；**安全**则看应用场合。

### 7.2 RTOS 与超级循环之争

这是嵌入式开发里真实的选型问题，也是把这一讲和 Lab 联系起来的地方。

**超级循环**（super loop）就是 `while(1)` 里把所有事轮着做一遍的写法——[[Lab1 寄存器、定时器与中断|Lab 1]] 和 [[Lab2 串行通信与PWM|Lab 2]] 写的都是这种结构。课件对它的评价是：**实现直观，而且贴合嵌入式系统的计算模型**，但有四个问题：

- 依赖**冗长的中断服务程序**（ISR）；
- 必须自己维持各个 ISR 之间的**同步**；
- **可预测性差**（尤其是中断嵌套时）**、可扩展性差**；
- 改一个 ISR 或改主循环，**影响会波及整个系统**。

RTOS 的做法是：**把所有计算请求都封装成任务**，按需求调度。好处是程序流程与事件响应更好、有（假象意义上的）**多任务**、**ISR 变得简短因而确定**、通信更好、资源管理更好。

课件给的例子是 **Keil RTX**（支持 ARM Cortex-M，带调度器、互斥量、事件、信号量、邮箱等），以及 **CMSIS-RTOS API**——一套通用的 RTOS 接口，ST 平台上的实现就基于 Keil RTX，并用到了一些 Cortex-M 专有指令。

> [!note] 这一节正好解释了 Lab 1、Lab 2 为什么是那个写法
> 两次实验都用超级循环加中断，并且踩到的正是课件列的那几条：中断里不能干重活（否则主循环被拖住）、ISR 之间要靠标志位同步、改一处牵动一片。
> 把这一节和 [[Lab1 寄存器、定时器与中断#4.4 为什么轮询不够，必须上中断|Lab 1 关于中断的那一节]]对着读，就能看出 RTOS 是在这些问题上再加一层抽象。

## 8 进程：这层假象的基本单位

### 8.1 一个进程手里有什么

一个进程可以拥有：**一份 CPU 时间配额**（相当于一颗虚拟 CPU，这正是操作系统扮演的角色）、**内存**（真实的或虚拟的）、**一个进程 ID**、以及**若干线程**。

那么，进程彼此知道对方存在吗？课件的回答很精确：

- 操作系统的职责就是**制造一种"这个进程拥有它执行所需的一切"的假象**；
- 这是对硬件资源的抽象——**每个进程都看见一颗专属处理器和一段专属内存**，尽管实际上它们常常是共享的；
- 但进程**可以**知道彼此，通过**进程间通信**（inter-process communication, IPC）。

### 8.2 执行现场摊开来长什么样

![[L04 进程的内存布局.png]]

图里四段的分工与各自的要点都标在旁边，这里只补两点容易考的：

- **静态数据分两层**：程序里已经赋了初值的，从程序文件读进来；**没赋初值的由系统置零或置空指针**——所以 C 里未初始化的全局变量一定是 0，而未初始化的局部变量（在栈上）是垃圾值。
- **代码段通常只读**，而 **PC（程序计数器）指着下一条要执行的指令**；**栈由 SP（栈指针）指着栈顶，后进先出**（FILO）。

### 8.3 程序、进程、任务、线程

这四个词在课件里有明确分工，考试爱考区别：

| 词 | 指什么 |
| --- | --- |
| **程序**（program） | 通常指**存在磁盘上的那些指令** |
| **进程**（process） | **程序加上它的执行上下文** |
| **任务**（task） | 有些系统（尤其嵌入式语境）这么叫；**本课程两个词互换使用** |
| **线程**（thread） | **轻量级进程**；一个进程可以有多个线程，它们**共享同一份系统资源**，所以创建、终止、切换、通信都更快 |

之所以需要"进程"这个抽象，是因为要在执行之间来回切换，操作系统就**必须把全部执行上下文记下来**。上下文包括：

- **内存状态**：代码、数据、堆、栈；
- **CPU 状态**：PC、SP 和其他寄存器；
- 还有**操作系统那一侧的状态**。

### 8.4 PCB：这份存档放在哪

这份"执行现场的存档"存在**进程控制块**（process control block, PCB；嵌入式语境里也叫 task control block, TCB）里。课件列的内容：

进程 ID、进程状态、（保存下来的）PC 与 SP 及其他寄存器、调度信息（优先级）、内存管理信息、记账信息、用户信息（含 IPC）、以及其他信息。

找到它的路径是两跳：**ID 指向进程表里的一项，那一项存着指向 PCB 的指针。**

### 8.5 创建与终止

**创建**的触发有三种：系统初始化时、某个进程提出请求、或用户提出请求。步骤是：分配一个唯一 ID（Linux 里是 `init_task_pid()`）；为 PCB 等内核控制结构以及用户内存分配空间；初始化 PCB 与内存管理信息；**把 PCB 挂进队列**。

**终止**则是：由操作系统或用户停掉，或者自己结束；处理好它的输出；释放资源、回收内存；把 PCB 从队列里摘掉。

> [!warning] 嵌入式这里有一条反直觉的规矩
> 课件原话：**在嵌入式软件里，有些进程永不终止；终止意味着出了故障。**
> 桌面系统上程序跑完就退出是正常的；嵌入式控制回路一旦退出，被控对象就失去了控制。写 Lab 代码时 `while(1)` 永不跳出，正是这条规矩的体现。

### 8.6 上下文切换要花多少钱

有了 PCB，**上下文切换**（context switching）就好办了：调度器要停下一个进程时，把硬件寄存器、程序计数器、内存状态（栈与堆）、以及进程状态存进它的 PCB；要启动另一个时，再从那一份 PCB 里读回来。

代价必须记住：**上下文切换是要花时间的，可能高达几千个 CPU 周期**，它是实打实的**开销和瓶颈**，而且还需要硬件配合。

这就是多道程序设计的全貌——**虽然任何时刻真正活跃的进程只有一个**，靠足够快的切换造出"同时在跑"的假象。假象越逼真，切换越频繁，这笔开销就越大。

> [!note] 把这个数字和 L03 挂起来
> 几千个周期是什么概念？按 [[L03 性能#2.1 时钟从哪来，三个名字各指什么|τ = 1/f]]，64 MHz 的机器上一个周期约 15.6 ns，几千个周期就是**几十微秒**。
> 对桌面系统这微不足道；对一个要求响应时间在百微秒级的控制回路，这就是必须算进预算里的一笔。RTOS 把 ISR 写短、把切换次数压下来，压的正是这笔钱。

## 9 进程状态与状态转换

### 9.1 五个状态

进程在生命周期里处于不同状态。变体很多，但**标准模型有五个**：

- **新建**（New）：刚创建，还没准备好进队列；
- **就绪**（Ready）：可以被操作系统装载了；
- **运行**（Running）：调度器从队列里挑中了它并让它执行，**通常只有一个**；
- **阻塞**（Blocked）：不在队列里，正在等待；
- **退出**（Exit）：做完了，需要终止。

### 9.2 六种转换，各自由什么触发

状态转换由三类事情引起：**操作系统的调度、外部中断、或程序自己提出的请求**。

![[L04 五状态模型与转换.png]]

图下方列出了六种转换各自的触发条件，和课件的说法一一对应。有两处特别容易答错：

- **事件发生之后不是直接回到运行，而是回到就绪。** 等到的只是"不缺别的东西了"，CPU 还得重新排队去抢。
- **超时（time out）包含两种情况**：时间片用完，以及被更高优先级的进程抢占。两者都把进程推回就绪队列。

### 9.3 状态、队列与上下文切换的关系

三条收尾的要点：

- 状态信息也记在 PCB 里；
- **只要进程离开或进入"运行"状态，就发生一次上下文切换**——这是把 [[#8.6 上下文切换要花多少钱|§8.6]] 那笔开销和这张状态图对上号的关键；
- 转换可能是**自愿的也可能是非自愿的**：正常结束程序属于前者，出错属于后者。

操作系统通常为**处于同一状态的进程**维护队列或类似队列的结构（链表之类），所以 PCB 里有大量指针；Keil RTX 里对应的是 `rt_list.c`。

模型还可以更复杂：有些进程在**就绪**或**阻塞**状态下会被挪到二级存储上去，于是"挂起的就绪"和"挂起的阻塞"各加一个状态，成为**七状态模型**，用来支持**交换**（swapping）；调度器会偏向选择仍在主存里的那些进程。

## 本讲速记

- 操作系统 = **抽象**（把琐碎的硬件藏起来）+ **资源管理**（把有限资源分好）+ **控制**（防止出错与滥用）。应用通过 **API** 请求服务，人通过**用户界面**打交道。
- 演进链条：无操作系统 → 操作员 → **批处理**（常驻监控程序）→ **多道程序**（动机就是缩短 CPU 被 I/O 阻塞的时间、提高利用率）→ **分时**（交互需求）→ 个人计算机。
- 抽象是**逐层**加的：`Read/Locate/Write` → `Write(..., LogAddr)` → `fprintf(FileId, ...)`。Unix 的口号是**一切皆文件**。三种视角：用户 / 应用开发者 / 操作系统程序员。
- 资源管理只有两招：**时间复用**（CPU 轮流用）与**空间复用**（内存切块分）。
- 内核结构：**单体**——全部代码一个程序，**快但一个 bug 拖垮全系统**；**微内核**——内核只留最必要的，其余做成用户态服务器，**好维护但切换与 IPC 开销大**。现代系统走**混合**（Windows NT、XNU）。
- **RTOS 的四条设计要求**：可预测性与确定性（第一位）、速度（**有时要拿确定性去换**）、响应性与用户控制、故障安全。**别把 RTOS 答成"更快的 OS"。**
- EOS 与 RTOS 本课程**互换使用**；嵌入式里**进程永不终止，终止即故障**。
- **超级循环 vs RTOS**：超级循环直观但 ISR 冗长、要手工同步、嵌套时不可预测、改一处波及全身；RTOS 把请求封装成任务来调度，ISR 简短因而确定。
- **程序**在磁盘上；**进程** = 程序 + 执行上下文；**任务**是同义词；**线程**是轻量级进程，**共享同一份系统资源**，故创建/切换/通信更快。
- 内存布局四段：**代码**（只读，PC 指着下一条）、**静态数据**（全局/常量/static，线程共享；未初始化的被清零）、**堆**（malloc/free，向上长）、**栈**（调用现场，SP 指栈顶，FILO，向下长）。堆栈相向而行，中间共用。
- **PCB/TCB** 存 ID、状态、PC/SP 与寄存器、调度信息（优先级）、内存管理信息、记账与用户信息。**ID → 进程表的一项 → 指向 PCB 的指针。**
- **上下文切换可达几千个 CPU 周期**，是开销与瓶颈；任意时刻真正活跃的进程只有一个，多任务是切换造出来的假象。
- **五状态**：新建 / 就绪 / 运行 / 阻塞 / 退出。六种转换：Admit、Dispatch、Time out、Event Wait、Event Occurs、Release。**事件发生后回的是就绪不是运行**；**超时既指时间片用完也指被抢占**。
- **进出"运行"状态就是一次上下文切换**。同状态的进程排在各自的队列里。把就绪/阻塞挪去二级存储，就扩成**七状态模型**，用于支持**交换**。
