Lecture 13 — Working Principles of Blockchain I

区块链工作原理（上）

一个没有中心机构的网络里，一笔交易怎样从某个用户手里出发，最后变成每个参与者账本里同一条记录，而且改了会被发现、改起来代价很高？

主线这一讲在做什么

这一讲回答一个问题：一个没有中心机构的网络里，一笔交易怎样从某个用户手里出发，最后变成每个参与者账本里同一条记录，而且改了会被发现、改起来代价很高？

回答分四步：

  1. 先要有人在网络里干活——用户和他们运行的节点（node，接入区块链网络、运行区块链软件的一台计算机）：入网要满足什么条件、有哪几类、各管什么；
  2. 记录装在区块（block，一批交易打成的一个包）里，块与块用哈希（数据的定长指纹，见 4.1）串成一条链，所以改动历史会被发现；
  3. 一笔交易从创建到被全网接受，课件列了 13 步；
  4. 最后用六层架构把前面这些部件按“离用户多近”归位。

课件前 9 页复习 L12，第 10–27 页其实是 L12 大纲里没讲完的两节（节点、分层；所以这些页的页眉还写着“Blockchain and Database Maintenance”），真正属于本讲大纲的只有第 30–32 页的工作流程。本笔记的顺序与课件有三处不同：节点职能表（p12）放到三类节点各自讲完之后，当汇总用；第 32 页的链式结构图提前到 13 步流程之前，因为第 7–13 步一直在操作“块”和“链”；六层架构从流程之前挪到最后，当一张地图，把讲过的东西逐层放回去。

1复习：L12 讲到哪里

课件 p2 列了 L12 大纲的四项：前两项（分类、数据库维护）是黑字，后两项（节点、分层）是灰字——意思是上次只讲完前两项。本节把前两项压缩成要点，细节在 L12 区块链系统概览。

1.1三类链与两种许可

课件 p3 给了两种分法。按谁在运营分三类：

  • 公有链（public blockchain）：任何人都能随时加入或退出、都能参与出块（产生一个新区块并把它接到链上），课件说它“Completely decentralized”（完全去中心化，decentralization：没有任何一方说了算；“完全”说得太绝对，L12 有讨论），例子是比特币；
  • 私有链（private blockchain）：由单一组织控制，节点加入要经这个中心实体许可，出块的节点事先指定；
  • 联盟链（consortium blockchain）：由多个组织共同控制，加入要经联盟成员许可，部分中心化。

按准入（access permission，加入网络、参与记账即出块要不要别人批准）分两类：

  • 无许可链（permissionless blockchain）：任何人都能加入、都能出块，不需要任何人批准；
  • 许可链（permissioned blockchain）：只有经批准的节点才能出块。

注意这里的 permissioned / permissionless 看的是出块（记账）权限。L11 p15 还有另一套两维分法：permissioned / permissionless 按“节点身份须不须已知”分，public / private 按“谁能读”分。两套里同一个词意思不同，口径以 L12 的两种分类法对照为准；考 public / private / consortium 的准入（模拟卷 Q3(a)(iii)），按本页这一套答。

p4 把两种分法画成一棵树：根是“Blockchain Classification”，分成 Permissionless 与 Permissioned 两支；Permissionless 下只有 Public，Permissioned 下有 Consortium 与 Private。联盟链和私有链都属于许可链，区别只在许可由谁发：私有链是一个组织，联盟链是一群组织。

模拟卷 Q3(a)(iii)：“Explain the access permission respectively for public chain, private chain and consortium chain. [3 marks]”参考答案就是 p4 左边的三行原文：

“Public blockchain network—permissionless / Private Blockchain Network—Permissioned / Consortium Blockchain Network—Permissioned”

题目用的是“Explain”，只写三个标签不够稳，每行补上期末总复习课件 L20S p14–p16 的原话：

  • Public — permissionless: “Any blockchain node can join or leave at any time. Any blockchain node can participate in mining process. Completely decentralized.”
  • Private — permissioned: “Nodes can join or leave the network with the permission from the central entity. Completely centralized. Miners are selected a priori.”
  • Consortium — permissioned: “Nodes can join or leave the blockchain network with the permission from the consortium of nodes. Not all the nodes can validate the transactions. Partially centralized.”

p5 列了公有链的五个一般性问题（只有名词，解释在 L12）：

1.2谁来维护账本

账本（ledger）在这里就是全部交易记录。p6–p7 比较“谁负责维护它”：

  • 集中式数据库（centralized database）：由一个中心实体维护，这个实体必须高度可靠、可信；
  • 分布式数据库（distributed database）：由几个指定的节点共同维护；
  • 区块链：没有可信的中心实体，账本由多个节点共同维护。三类链的差别正在“由谁维护”：公有链是全体节点，联盟链是一组联盟节点，私有链是一个或少数几个节点（接近集中式系统）。

p8 列了区块链与 DBMS（Database Management System，数据库管理系统：传统数据库软件，如 MySQL）比较的六个方面，只有名称，对比结论在 L12 区块链系统概览。下表是课件的口径，它拿来比的其实是中心化数据库；L12 指出分布式数据库同样要共识、要把更新复制到各副本，不能一概而论：

方面传统数据库（课件口径，实指中心化数据库）区块链
Hashing（哈希）一般不对每条记录做哈希哈希贯穿始终：串链、算交易摘要、出块竞争
Public/Private Key（公私钥）一般不用必需：交易靠私钥签名授权
Sequence of Records（记录顺序）不必按序必须按序并互相链接
Consensus（共识：让各节点对账本内容取得一致）不需要必需：没有中心裁决者，多份副本只能靠共识统一
Immutability（不可篡改）记录可改已上链的记录改了会被发现、改起来代价很高（4.3）
Ledger Dissemination（账本传播）更新不必广播每次更新都要传遍全网

这张表里的哈希、公私钥、记录顺序、共识、传播，就是本讲第 2–5 节要逐一落地的东西。

2入网的两个前提

p11：“Before the user/node is considered as part of the blockchain network”，必须做到两件事。

2.1一对密钥就是身份

“User/node has to generate public/private key pair for authentication purpose.”

公私钥对（public/private key pair）是 L7 公钥密码 的内容：私钥自己保密，公钥公开，私钥做的签名任何人都能用公钥验证。区块链里没有“注册账号”这一步——自己在本地生成一对密钥，就有了身份：

  • 地址（address，收款时给别人的那串字符）由公钥经哈希得到。比特币取公钥哈希再编码；以太坊取公钥的 Keccak-256（以太坊所用的一种哈希函数；它和标准化后的 SHA3-256 填充规则不同，输出也不同）哈希值的后 20 字节，加前缀 0x。
  • 花钱时用私钥对交易签名，别人用公钥验签，就确认“这笔交易确实是这个地址的主人发的”，私钥本身从不离开主人。这就是 p11 说的 authentication（认证：确认对方是谁）。
  • 反过来，谁拿到私钥谁就是主人；私钥丢了，这个地址上的钱就再也动不了，没有任何机构能“找回密码”。

2.2至少要有几个直接相连的邻居

“User/node has to establish a minimum number of peer connection (direct connections) with other nodes in the blockchain network.”

区块链网络是 P2P 网络（peer-to-peer，对等网络：没有中心服务器，每个节点既向别人要数据、也给别人供数据）。一个节点和另一个节点之间有一条直接的连接，彼此就是对等节点（peer）。一笔交易或一个新块，是靠“每个节点转发给自己的邻居”一跳一跳传遍全网的。

为什么要规定“最少”：

  • 邻居太少，消息到你这里要绕很远，甚至一个邻居掉线你就断网了；
  • 更危险的是，如果你的邻居全被攻击者控制，你看到的就全是他想让你看到的交易和块，你却以为自己在看全网——这叫日蚀攻击（eclipse attack：把一个节点和诚实网络隔开，像月亮挡住太阳）。连接数越多，全被控制的可能越小。

比特币的参考客户端（Bitcoin Core）默认主动向外建立 8 条完整转发交易和区块的连接，新版另加 2 条只转发区块的连接，专为抵抗日蚀攻击。刚启动、一个邻居都不认识时，靠客户端里写死的一份 DNS 种子（DNS seeds：几个域名，查询它们能拿到一批在线节点的 IP 地址）找到第一批邻居（L14 p28 提到这份“hard code list”）；DNS 种子查不到时，客户端里还写死了一份备用的节点地址（fixed seeds）。

模拟卷 Q4(c)(iii) 把“How nodes join and leave the blockchain network?”列为区块链用于认知无线电网络的一个挑战，说的就是这两个前提在无线网络里不好满足（节点频繁移动、时有时无）。

3节点：三套分类

3.1三套分类各按什么分

p13 一口气列了三组名字，它们是三个不同维度的分类，同一个节点可以同时属于每组中的一类：

分类依据类别回答的问题
存多少账本、承担什么功能全节点（Full）、轻节点（Lightweight）、矿工节点（Miner，课件括注“Functionality Nodes”）这台机器是什么配置
在出块中的角色（“In terms of dealing with transactions”）领导者（Leader）、验证者（Validator）这一块由谁出、由谁查
在一笔交易中的角色发送方（Sender）、接收方（Receiver）这一笔交易是谁发的、谁收的

第一组不是互斥的划分：矿工节点在存储上就是全节点，只是多了出块的功能；p12 表把三者分成三列，是按“主要承担什么功能”看的。例如一台比特币矿机：它存完整账本（矿工节点，也是全节点）；它挖出某个块时是这一块的领导者，别人出块时它是验证者；它给别人转账时是发送方。

3.2全节点：存全账，自己验证

p14 三条：

  1. “Keep the full copy of the blockchain ledger locally.”——本地存一份从第一个块到最新块的完整账本。
  2. “Participate in transaction verification without reference to any node externally.”——验证交易时不问任何别的节点。
  3. “Participate in routing.”——参与路由（routing，在这里指把收到的交易和块转发给邻居）。

第 2 条是全节点的本质：它从创世块起把全部历史处理过一遍，所以知道当前每一笔钱在谁手里、有没有被花过，就能自己检查一笔交易的签名对不对、它花的钱以前有没有被花过，不必相信任何人。所以全节点是网络里不需要信任别人的那类参与者。（课外：比特币的“修剪模式”节点处理完历史后只留最近的一部分区块，照样能完整验证——要的是处理过全部历史，不一定要一直存着。）

3.3轻节点：只存区块头

p15 两条：

  1. “Only keep the header of each block and then reference to the external nodes when complete information is required.”
  2. “Participate in routing.”

区块头（block header）是一个块开头那一小段元数据：前一块的哈希、时间戳、全部交易的一个摘要等，比特币里固定是 80 字节，字段在 L14 的区块头一节逐个拆开。交易本身在块的其余部分，体积大得多。

只存头有多省：比特币平均 10 分钟一个块，一年的区块头总量是

80 B × 6 块小时 × 24 × 365 = 4,204,800 B ≈ 4.2 MB

和比特币白皮书（Nakamoto 2008）第 8 节的“4.2MB per year”一致；完整账本则是几百 GB。手机钱包因此大多是轻节点。

轻节点要确认“我收到的那笔钱确实被写进了某个块”时，向全节点要一份很短的证明，用自己存的区块头核对——这套方法叫 SPV（Simplified Payment Verification，简化支付验证），证明的原理是 Merkle 树（把一个块里的全部交易两两哈希、层层合并成一个值的树），见 L14 的 Merkle 证明。代价是它不能独立检查交易是否合法，只能相信“多数算力认可的链上的东西是对的”。

3.4矿工节点：唯一能往链上加块的

p16 两条：

  1. “Carry the consensus mechanism and responsible to publish the block in the blockchain.”
  2. “The most powerful nodes in the blockchain network, which can change the state of the blockchain network.”

加上课件用蓝色下划线标出的一句：“A node in a blockchain, which participates in consensus mechanism, i.e., miner node can create and add a block to the blockchain.”

两个词先说清：

  • 共识机制（consensus mechanism）：让互不信任的节点对“下一个块是什么”取得一致的规则。L15–L17 专门讲。
  • 挖矿（mining）：比特币式共识里，矿工反复做哈希计算、争抢出下一个块的权利，谁先算出符合要求的结果谁出块，并得到奖励。这种共识叫工作量证明（Proof of Work，PoW），L15 讲。

“most powerful”指的是写权：账本只有在加了一个新块之后才会变，而只有矿工能加块，所以只有矿工能改变账本的状态。它不等于“想写什么就写什么”——矿工出的块要被其他节点逐项检查，含非法交易的块会被拒收（第 9 步）。矿工也要存完整账本（p12 表第一行），因为打包之前它得先确认每笔交易合法。

逐行读：

  • 账本副本：全节点、矿工存完整的，轻节点只存一部分（就是区块头）。
  • 产生交易：全节点和轻节点是普通用户用来发交易的；表格把矿工当作只管出块的功能角色。
  • 参与共识：只有矿工。
  • 转发消息并验证：三类都参与，P2P 网络靠每个节点转发才能传开；注意这一行名字里带着 verification。
  • 验证交易：表格只给矿工打了 Yes。
勘误这张表有两格与课件别处或事实冲突

全节点的“验证交易”一格与 p14、L14 p31 冲突。 课件 p14 说全节点“Participate in transaction verification without reference to any node externally”，下一讲比特币一页（L14 p31）也说“Full nodes (including miners) check different fields of the block and its validity”；按比特币的实际，独立验证每一笔交易是全节点的定义（3.2），这一格应为 Yes。表格也有另一种读法：第四行“Routing for message dissemination and verification”已给全节点记了 verification，最后一行“Transaction validation”可能专指出块时把交易验证并写进块（矿工的共识职能）。两种读法的应试结论相同，见本框最后一段。

矿工的“产生交易”一格在现实中也不成立。 矿工每出一个块，都会在块里放一笔给自己发奖励的交易，叫 coinbase 交易（区块里的第一笔交易，凭空产生新币奖励出块者）；矿机的主人也完全可以像普通用户一样转账。表格表达的是“按功能角色划分”，不是说矿工被禁止发交易。

考场上：问“哪类节点能产生新交易”，按表答（模拟卷就是这样给分的）；问“全节点做什么”，按 p14 答，写上它独立验证交易。两处不要混用。

模拟卷 Q3(a)(i)：“List three different nodes in blockchain system, and indicates which node can generate new transactions. [4 marks]”

答法Q3(a)(i) 答法

Three types of nodes: full node, lightweight node and miner node.

  • Full node: keeps a complete copy of the ledger and verifies transactions by itself;
  • Lightweight node: keeps only the block headers and asks full nodes when complete information is needed;
  • Miner node: takes part in the consensus mechanism and creates new blocks.

Full nodes and lightweight nodes can generate new transactions.

参考答案只要求三个名字加最后一句；每类补一行职能，是防止阅卷人认为“列名不够”。

3.6按出块角色：领导者与验证者

p17：

  • 领导者节点（leader node）：“Leader nodes are those blockchain nodes that create blocks.” “The leader nodes can be elected and serves during a specific time.”
  • 验证者节点（validator node）：“Validator nodes are those blockchain nodes which validate the blocks.”
  • “In some blockchain, any node can be served as a leader/validator node”

一个块由谁出，不同的共识机制给出不同的答案，后面几讲会一一遇到：

  • PoW（L15 区块链共识 I）：每个块的领导者是本轮最先算出结果的矿工，不选举，每块重新竞争；所有其他节点充当验证者。
  • RAFT（一种靠选出领导者来让多台机器保持一致的共识算法，L16 区块链共识 II）：领导者由投票选举产生、在一个任期内负责，正对应“elected and serves during a specific time”。
  • PBFT（Practical Byzantine Fault Tolerance，实用拜占庭容错：即使有部分节点恶意乱发消息也能达成一致的投票式算法，L16 区块链共识 II）：有一个轮换的主节点负责提议，其余节点投票确认。

领导者–验证者的划分说明了一件事：出块的人和检查块的人是分开的，出块者无法自己给自己的块盖章放行。

3.7按单笔交易角色：发送方与接收方

p18：

  • 发送方节点（sender node）：“Sender nodes can creating transaction and issue a transaction to multiple blockchain nodes.” “Sender nods have to sign transactions with their individual private key”（“have to sign transactions”是课件的红字强调）。
  • 接收方节点（receiver node）：“Receive transactions issued by sender nodes.”

这里的“接收方”指收到这笔交易广播的那些节点，不一定是收款人。

为什么发送方必须签名：P2P 网络里谁都能广播任何东西，如果交易不带签名，任何人都能编一笔“从你的地址转给我”的交易。用私钥对交易做的数字签名（digital signature，见 L8 数字签名、证书与 PKI）同时给出三样保证：

  • 认证：只有私钥主人做得出这个签名，所以交易确实出自该地址的主人；
  • 完整性：交易里任何一个字（收款地址、金额）被改，签名就验不过；
  • 不可否认：主人事后无法抵赖自己发过这笔交易。

任何节点都能用发送方的公钥验签，不需要问任何机构。

4链：用哈希把块串起来

课件 p32 用一张三块的图说明块与块怎样连起来。所用的工具（哈希函数）和“改一块会怎样”的玩具链，L11 分布式账本与区块链导论 已经讲过；本节先用几行回顾，再读 p32 这张图，把两种篡改情形分开算一遍，最后指出图里的错误。

4.1回顾：哈希函数的性质

哈希函数（hash function）把任意长度的输入压成固定长度的输出，叫哈希值（hash value，也叫摘要 digest），可以当作数据的指纹。区块链最常用的 SHA-256（Secure Hash Algorithm 256）输出 256 位，写成 64 个十六进制字符。定义、性质与雪崩实测见 L11 的哈希一节，要点是：

  • 两个基本行为：定长（输入多长都输出 256 位）、确定（同样的输入永远得到同样的输出，任何人都能复算核对）。
  • 三条安全性质，都是“计算上找不到”——不是不存在，而是在可行的计算量内找不到：
    • 抗原像（preimage resistance）：已知哈希值，找不出对应的输入，只能一个个试。L15 的 PoW 靠这一条。
    • 抗第二原像（second-preimage resistance）：已知一份数据，找不出另一份哈希相同的数据。篡改检测直接靠这一条：攻击者改了数据，就没法让它的哈希保持原样。
    • 抗碰撞（collision resistance）：找不出任意两个哈希相同的输入。输入有无穷多种、输出只有 2256 种，碰撞必然存在，只是找不到；抗碰撞比抗第二原像要求更强，满足前者就满足后者。
  • 雪崩效应（avalanche effect）：输入改一点，输出大约一半的位翻转。L11 的实测是“A->B 5”与“A->B 9”的 SHA-256 有 119 位不同。

（《Lab3-4 区块链与 PoW 的 Python 实现》列的四条——确定性、雪崩、抗原像、抗碰撞——是同一套东西的另一种分法；问“哈希函数的安全性质”，按上面三条答。）

4.2每一块记住前一块的哈希

p32 的三个块，每块正面从上到下是四格：块号“Block # 1/2/3”、“Prev. Hash”（前一块的哈希）、“Hash”（本块的哈希）、“Data Transactions”（交易数据）。红色折线箭头从块 1 的 Hash 指向块 2 的 Prev. Hash，再从块 2 的 Hash 指向块 3 的 Prev. Hash；同一个值用同一种颜色（块 1 的 Hash 和块 2 的 Prev. Hash 都是黄字 0abe0237df）。左边一个大括号把前三格标为“Block Header”，块 1 下方标“Genesis Block”。

图要说的只有一句：后一块的 Prev. Hash 等于前一块的 Hash。 L11 讲的是同一个机制，这里补上它的名字和课件的画法：

  • 存着“前一块的哈希”的那个字段，叫哈希指针（hash pointer）：它既像普通指针一样告诉你前一块是哪一个，又附带了前一块内容的指纹，能用来核对前一块有没有被改过。L14 p17 的说法是“Hash pointer is responsible for pointing out the previous hash”、“hash pointer can also be used to verify the integrity of the blockchain”。
  • 第一个块前面没有块，叫创世块（genesis block），它的 Prev. Hash 填一个约定值（这里是全 0）。课件把创世块编为“Block # 1”，L11 的玩具链和比特币都从 0 编起，只是编号习惯不同。
  • 块的哈希是对块的内容算出来的，而 Prev. Hash 也是块内容的一部分。于是每一块的哈希都间接包含了它之前所有块的内容。

4.3篡改的两种情形

用一个简化模型实算，块号按 p32 从 1 起：

Hi = SHA-256(Hi − 1‖datai),H0 = 32 个零字节

‖ 表示把两段字节首尾拼接。拼接口径要说清，因为口径不同，算出的值就不同：这里 Hi − 1 以 SHA-256 输出的 32 个原始字节参与拼接（显示时才写成 64 位十六进制），data 取 UTF-8 字节。L11 的玩具链用的是另一种口径：把前一块哈希当作 64 个字符的十六进制字符串，再拼交易文本；实验《Lab3-4 区块链与 PoW 的 Python 实现》则是把整块字典（其中 previous_hash 也是十六进制字符串，创世块填 '0'）用 json 编码后整体哈希。按十六进制字符串的口径，下面块 1 的哈希会是 d88d3468… 而不是 0bcc65f1…。三种口径的数不同，机理相同。

三块的数据分别是 genesis-data、block2-data、block3-data。篡改者把块 1 的数据改成 genesis-DATA（改了 4 个字母的大小写）之后，有两条路：

块原始链情形①：只改块 1 的 Data情形②：再把后面各块的 Prev. Hash 一路改掉
1（创世块）0bcc65f1…c52c66e4…c52c66e4…
2（Data 没改）aaf2e7d3…aaf2e7d3…（不变）b074b851…
3（Data 没改）782585e5…782585e5…（不变）20f40c72…

上：原始链。中：情形①，只有块 1 的 Hash 变，块 2 存的 Prev. Hash 仍是旧值，链接断开。下：情形②，后面各块的 Prev. Hash 被一路改掉，每一块的 Hash 都变了。红色是变了的值。

情形①：只改块 1，别的不动。 块 1 的哈希由 0bcc65f1… 变成 c52c66e4…；块 2、块 3 的内容（包括块 2 里存的 Prev. Hash 0bcc65f1…）一个字没动，所以它们的哈希也不变。但块 2 存的 Prev. Hash 与块 1 现在的哈希对不上——链在块 1 和块 2 之间断开，任何人复算一次就能发现。

情形②：把后面的链接一路接上。 篡改者把块 2 的 Prev. Hash 改成 c52c66e4… → 块 2 的内容变了 → 块 2 的哈希变成 b074b851… → 块 3 的链接又断了，于是再改块 3……一路改到最新的块。改完后他手里这条链内部完全自洽，但：

  • 网络里其他成千上万个节点的副本还是原始链，链尾哈希 782585e5… 与他的 20f40c72… 一比就露馅；
  • 在 PoW 链上，每个被改的块都要重新挖矿，而且要比全网诚实矿工更快地追上最新的块，代价高到不现实，见 L15 区块链共识 I。

易错哈希链本身只让篡改被发现，代价高要靠副本和 PoW

误：区块链用哈希“锁住”了数据，所以数据改不了。

正：任何人都能在自己电脑上改一份账本。哈希链保证改了会被发现；成千上万份副本让单方面的改动无人认可；PoW 让重做后面所有块的代价高到不现实。少了后两样（比如只有一个人保存的哈希链），情形②只是多算几次哈希而已。

还有一个漏洞：链尾那一块没有后继块，改了它，没有下一块的 Prev. Hash 来暴露它，单靠哈希链查不出来，要靠 PoW 条件（它的哈希不再满足难度）或与别人的副本比对。实验《Lab3-4 区块链与 PoW 的 Python 实现》的校验一节专门用测试验证了这一点。

实验里的 is_chain_valid() 逐块检查三件事：previous_hash 是否等于前一块的哈希（就是情形①的检测）、index 是否等于位置、哈希是否满足难度。实验的区块是一个含 index、timestamp、data、proof、previous_hash 五个键的字典，用 JSON（JavaScript Object Notation：把字典、列表写成文本的通用格式）编码后整体做 SHA-256。真实的比特币有一处不同：它只对 80 字节的区块头算哈希，交易通过区块头里的一个摘要间接进入，见 L14 的哈希指针一节。

4.4课件链式图的四处问题

勘误p32 示意图的四处错误
  • 块 3 的 Hash 与块 1 的 Hash 完全相同（都是 0abe0237df）。两个内容不同的块哈希相同，等于找到了 SHA-256 的碰撞，实际不会发生，是制图时复制粘贴留下的。
  • 8dbke8930 不是合法的十六进制数：十六进制只有 0–9 和 a–f，里面的 k 不可能出现；它也只有 9 位，和 0abe0237df 的 10 位不一致。示意图可以截短哈希，但不能出现非法字符。
  • “Block Header”大括号把块自己的 Hash 也括了进去。 块自己的哈希是对区块头算出来的，算之前它还不存在，所以它不是区块头里的字段，也不存储在块里（比特币就是这样，见 L14 的区块头字段）。图里画出来只是为了方便看出链接关系。
  • 创世块标成“Block # 1”。比特币里创世块的编号（高度）是 0。这只是编号习惯，不影响理解。

5一笔交易的 13 步

课件 p30–p31 标题是“General Working Sequence of Blockchain”，把一笔交易的一生拆成 13 步。下图按阶段分成三列。

13 步分成三段：交易产生并进入交易池（蓝），矿工把交易打包成块并出块（黄），新块传遍全网并被接受（绿）。

5.1交易阶段：第 1–6 步

  1. “Blockchain user(s) creates account(s).” 用户创建账户。按 2.1，就是在本地生成一对密钥、由公钥得到地址，不需要向任何人登记。
  2. “Blockchain user creates transaction (Tx).” 用户创建一笔交易（transaction，缩写 Tx：一条“把多少钱或什么数据从谁那里转给谁”的记录）。
  3. “Transactions are signed.” 发送方用私钥对交易签名，即 3.7 的红字“have to sign transactions”。
  4. “Transaction is broadcast to the validating nodes.” 交易被广播（broadcast：发给所有邻居，邻居再转发给它们的邻居）到负责验证的节点，靠的是 2.2 的对等连接。
  5. “Transaction is validated.” 收到交易的节点各自检查：签名能否用发送方公钥验过；发送方有没有足够的钱；这笔钱是否已经花过。最后一项防的是双花（double spending：同一笔钱花两次，例如同时发两笔交易把同一笔钱分别付给两个人）。不合格的交易直接丢弃、不再转发。
  6. “Transactions are gathered in a pool.” 通过验证的交易进入交易池（transaction pool，比特币里叫 mempool：已验证、还没被写进任何块的交易的等候区）。每个节点各有一个自己的交易池。

到这一步为止，交易只是“被网络知道了”，还没有写进账本。

5.2出块阶段：第 7–10 步

  1. “Miner node(s) gather multiple Txs and create block.” 矿工从交易池里挑一批交易（通常优先挑手续费高的；transaction fee：发送方附在交易里、付给打包它的矿工的费用），加上自己的 coinbase 交易，组成一个候选块，并把当前最新块的哈希填进这个块的 Prev. Hash（4.2）。
  2. “Miner node(s) perform mining.” 矿工挖矿，争夺这一块的出块权（3.4；具体怎么算在 L15 区块链共识 I）。很多矿工同时在挖，各自的候选块内容可能不同。
  3. “Block validation is carried out.” 检查这个块：工作量是否达标、块里每一笔交易是否都合法、Prev. Hash 是否指向一个已知的有效块。它通常就是最新的块；若两个矿工几乎同时出块、后来的块指向了别的块，就形成分叉，接哪一支由 L15 的最长链规则取舍，不在“合不合法”的检查之内。
  4. “Successful miner node adds block to the blockchain.” 胜出的矿工把块接到链上。

第 9 步由谁做，课件这里没说。下一讲比特币的流程（L14 p31）把“全节点检查块的各个字段和有效性”放在矿工广播之后。两种说法并不矛盾：出块的矿工自己先检查一遍，收到块的每个节点在接受之前再独立检查一遍——后者才是这一步真正的意义，它让出块者无法夹带私货（3.6）。

5.3传播与确认：第 11–13 步

  1. “Added block information is broadcast to the blockchain network.” 新块广播到全网。
  2. “Blockchain node adds the broadcast block to their local copy of blockchain—Block confirmation.” 各节点把收到的块加到自己的本地副本上，课件把这一步叫作区块确认（block confirmation）。全节点存整块，轻节点只存它的区块头。
  3. “Block becomes part of the global blockchain—Block published.” 块成为全网公认的那条链的一部分，课件叫区块发布（block published）。
易错“确认”在课程里有两个意思

本讲 p31 的“Block confirmation”指一个节点把广播来的块加进本地副本，是一个瞬间动作。

L15 讲共识性能指标时的“Block Confirmation Time”（“A new block must wait before it is confirmed”）指一个块后面再接上若干个块之后，才被认为足够可靠。原因是：两个矿工几乎同时出块时，链会暂时分叉，较短的那支（准确说是累计工作量较小的那支）最终被放弃，上面的块作废；一个块后面接的块越多，它所在的那支被放弃的可能就越小。比特币的习惯是等 6 个块。

模拟卷 Q3(b)(iii) 用的是后一个意思：“it requires to wait for 20 blocks to confirm any new block”，平均确认时间 = 20 × 200 s = 4000 s（约 66.7 分钟）。计算题见 L15 区块链共识 I。

考场上看到“confirmation time”“wait for N blocks”，用 L15 的意思；只有问“一般工作流程”时，才按本讲第 12 步写。

和比特币白皮书的原始描述对照（课件外）

中本聪 2008 年的白皮书第 5 节“Network”只写了 6 步：

  1. 新交易广播到所有节点；
  2. 每个节点把新交易收集进一个块；
  3. 每个节点为自己的块寻找工作量证明；
  4. 找到的节点把块广播给所有节点；
  5. 节点只接受其中所有交易都有效、且没被花过的块；
  6. 节点表示接受的方式，是在挖下一个块时把这个块的哈希当作 Prev. Hash。

课件的 13 步比它多出了创建账户（第 1 步）、签名（第 3 步）、交易池（第 6 步），以及“confirmation”“published”两个命名。白皮书第 6 步值得注意：节点“接受”一个块，不是投票，而是在它后面接着挖——L15 讲 PoW 时的“最长链”规则就来自这里。

5.413 步由谁来做

6六层架构

6.1六层与每层的例子

p20：“We can divide the blockchain system into six layers”。p21 是同一套六层的彩图，每层右边列了该层的例子：

按课件 p21 重画。原图共识层是浅黄底白字，几乎看不清，这里重新上了色。

读图的顺序：从上往下，越靠上越接近用户，越靠下越接近机器——用户在最上层的钱包里点“转账”，最终变成最下层 CPU（中央处理器）上的一次次计算。左边那根贯穿六层的竖条“Type of Blockchain (Public, Private, Consortium)”表示：链的类型不属于某一层，而是影响每一层的选择。例如许可链只有被授权的节点能出块，参与共识的成员是一份确定的名单，共识层就可以让这些成员投票，用 PBFT；无许可链谁都能加入，成员不固定、也数不清，只能用 PoW、PoS（Proof of Stake，权益证明：按持有的币量而不是算力选出块者）这类不依赖身份的共识。

和计算机网络的分层（OSI 七层模型：开放系统互连参考模型，把网络通信从物理信号到应用分成七层）同理，分层的作用是定位：任何一项区块链技术都能问“它属于哪一层”，每层只依赖下层提供的服务。p20 写“Network and Operating System Layer”，p21 写“Network and OS Layer”，是同一层。

6.2逐层说明

应用层（Application Layer，p22）：“It directly interacts with the user”；“different applications run over the client and the client uses the applications to interact with the blockchain system.”——用户直接打交道的那一层，各种应用跑在客户端上，通过它们使用区块链。p21 的例子：

  • Cryptocurrency：加密货币，如比特币；
  • Dapps（decentralized applications，去中心化应用：后端逻辑跑在区块链上而不是某家公司服务器上的应用）；
  • IoT（Internet of Things，物联网）、5G：把区块链用在设备网络与移动通信里，是本课 L18–L20 的方向；
  • Record Management：记录管理，如病历、证书存证；
  • Wallet（钱包：保管私钥、构造交易并发起签名的软件，第 1–3 步由它发起；签名所用的算法属于数据组织层的 Cryptographic Algorithms）；
  • ChainCode（链码：Hyperledger Fabric——Linux 基金会主导的许可链平台，常用于联盟场景——对智能合约的叫法）。

虚拟化与智能合约层（Virtualization and Smart Contract Layer，p23）：“responsible for virtualization and smart contract related execution”；“also interacts with the user machine and responsible to compile blockchain code.”

  • 智能合约（smart contract）：部署在链上的一段程序，由交易触发，网络里每个节点都执行一遍、结果写进账本。比特币几乎不支持，以太坊的核心就是它（L14 的以太坊一节）。
  • 例子里的 Compilers（编译器：把合约源代码翻译成链上能执行的字节码）、Distributed Virtual Machines（分布式虚拟机：每个节点上都跑一个相同的执行环境，如以太坊虚拟机 EVM，Ethereum Virtual Machine）、Dockers（Docker 容器：Hyperledger Fabric 把链码放在容器里隔离运行），都是为“让合约在每个节点上以相同方式运行”服务的。

共识层（Consensus Layer，p24）：“responsible to manage and reach consensus in a P2P network”；“operates and interacts at network level”；“It dictates which consensus protocol needs to be executed and how to follow the rules to achieve consensus.”——决定用哪种共识协议、按什么规则达成一致，第 7–10 步发生在这里。p21 的例子（后面三讲逐个展开）：

  • PoW（Proof of Work，工作量证明）：靠算力竞争出块，L15；
  • PoS（Proof of Stake，权益证明）：按持有并锁定的币的多少来选出块者，不必拼算力，L15；
  • PoW-PoS（课件写作“Pow-PoS”）：两者混合；
  • BFT（Byzantine Fault Tolerance，拜占庭容错：即使有部分节点恶意乱发消息，诚实节点仍能达成一致）；
  • PBFT（3.6 提过）：BFT 的一个可实际运行的投票式算法，L16–L17；
  • Ripple：Ripple 公司的网络（XRP Ledger）所用的共识，由各节点信任的一组验证者投票。严格说 Ripple 是公司和网络的名字，协议另有名字。

模拟卷 Q3(b)(ii)“List any three consensus mechanisms used in blockchain systems [3 marks]”，参考答案“PoW, PoS, RAFT, Paxos, PBFT, etc.”（Paxos 与 RAFT 同属靠节点投票达成一致的共识算法，L16 讲），这一行例子里就能挑出三个。

网络与操作系统层（Network and OS Layer，p25）：“the core layer responsible for managing the underlying network services and operations over a blockchain network”；“communication mechanism, peer discovery, routing, and peer-to-peer network are managed.”——2.2 的对等连接、找邻居（peer discovery，节点发现）、转发交易与块（第 4、11 步）都在这一层。

数据组织与拓扑层（Data Organization and Topology Layer，p26）：“responsible for data organization and topology management”；“It includes tasks such as hashing, data storage cryptographic algorithms, data ordering, side chain, sharding, and off-chain related issues.”（“data storage”后面漏了逗号，对照 p21 是两项）；“It also includes issues such as transaction models, and Merkle Tree management.”

  • Hashing 与链式结构：第 4 节整节；
  • Cryptographic Algorithms：签名与验签算法（第 3、5 步）；
  • Ledger Storage：账本怎么存，全节点存整本、轻节点只存头（第 12 步）；
  • Data Ordering (Linear, DAG)：记录排成一条线（普通区块链），还是排成 DAG（directed acyclic graph，有向无环图：每条记录可以同时指向好几条更早的记录、但不会绕回自己；面向物联网的账本 IOTA 用这种结构）；
  • Transaction models：交易模型，比特币记“未花费的交易输出”（UTXO，Unspent Transaction Output）、以太坊记“账户余额”，L14 讲；
  • Merkle Tree：把一个块里全部交易压成一个摘要的树，L14 讲；
  • Sidechain（侧链）、Sharding（分片）、Off-chain（链下）：三种扩容手段，L14 讲侧链与链下、L14 讲分片。

硬件层（Hardware Layer，p27）：“This layer deals with the underlying hardware of the blockchain nodes. The performance of blockchain nodes depends upon the architecture used, i.e., whether its CPU or GPU, etc.”——节点跑在什么硬件上，决定了它算得多快。挖矿就是大量重复的哈希计算：GPU（图形处理器，有成千上万个能并行做简单运算的核心）比 CPU 快得多。（课件外：比特币挖矿如今已被 ASIC（application-specific integrated circuit，专用集成电路：这里指只为算 SHA-256 而设计的芯片）垄断，CPU、GPU 早已不划算。）

补充这套六层不是公认标准

课件没有注明六层模型的出处，文献里有好几种分法。中文资料里最常见的是另一套六层：数据层、网络层、共识层、激励层、合约层、应用层（袁勇、王飞跃，《区块链技术发展现状与展望》，自动化学报，2016）。两套名字有重叠但不一一对应，例如课件没有“激励层”，却多了“硬件层”和“虚拟化”。考试按课件这一套答，别把中文资料的版本串进来。

本讲速记

  • 课件前半复习 L12：三类链 public（permissionless）/ private（permissioned，单一组织发许可）/ consortium（permissioned，多个组织共同发许可）；联盟链和私有链都是许可链。公有链五个问题：交易少、可扩展性、假名、区块容量有限、耗能。区块链与数据库比六方面：哈希、公私钥、记录顺序、共识、不可篡改、账本传播。
  • 入网两前提（p11）：生成公私钥对用于认证（密钥对就是身份，地址由公钥哈希得到）；与其他节点建立最少数量的直接对等连接（太少会被孤立或被日蚀攻击）。
  • 三套节点分类是三个维度：存储/功能（full、lightweight、miner）；出块角色（leader、validator）；单笔交易角色（sender、receiver）。同一节点可兼属。
  • 全节点：存完整账本、不问别人自己验证交易、参与转发。轻节点：只存区块头，需要时问外部节点（SPV），一年的区块头约 4.2 MB。矿工：执行共识、发布区块，唯一能往链上加块，所以“most powerful”。
  • 职能表（p12）：产生交易 = full、light（Yes），miner（–）；参与共识 = 只有 miner；转发 = 三类都参与；验证交易 = 表上只有 miner。表中全节点“验证交易”为“–”与 p14、L14 p31 冲突，按实际应为 Yes（第四行“转发消息并验证”已给全节点记了 verification）；矿工实际会产生 coinbase 交易。答“谁能产生交易”按表：full node 和 lightweight node。
  • Leader 出块，可被选举、在一段时间内服务；validator 验证块；有的链任何节点都可当 leader/validator。Sender 创建并广播交易，必须用私钥签名；receiver 收到交易广播。签名提供认证、完整性、不可否认。
  • 哈希链（L11 讲过机制）：后一块的 Prev. Hash = 前一块的 Hash（哈希指针）。只改一块 → 只有它的哈希变，下一块的链接断；把后面的 Prev. Hash 一路改掉 → 之后每块哈希都变，但与别人的副本对不上、PoW 链上还要重挖。哈希链做到篡改可检测（tamper-evident），副本加 PoW 做到篡改代价高（tamper-resistant）；链尾一块单靠哈希链查不出。篡改检测靠哈希的抗第二原像。p32 图：块 3 与块 1 哈希相同、8dbke8930 含非十六进制字符、块自己的 Hash 不在区块头里。
  • 13 步：① 建账户 ② 建交易 ③ 签名 ④ 广播给验证节点 ⑤ 验证交易 ⑥ 进交易池 ⑦ 矿工收集交易组块 ⑧ 挖矿 ⑨ 验证区块 ⑩ 胜出矿工加块 ⑪ 广播新块 ⑫ 各节点加入本地副本——Block confirmation ⑬ 成为全局链的一部分——Block published。
  • 本讲的“Block confirmation”＝节点把块加进本地副本；L15 的“确认时间”＝等后面 N 个块，模拟卷 20 块 × 200 s = 4000 s。两者不同。
  • 六层（上→下）：应用层（Cryptocurrency, Dapps, IoT, 5G, Record Management, Wallet, ChainCode）；虚拟化与智能合约层（Compilers, Distributed VMs, Smart Contract, Dockers）；共识层（PoW, PoS, PoW-PoS, BFT, PBFT, Ripple）；网络与 OS 层（P2P, Communication Mechanism, Peer Discovery, Routing）；数据组织与拓扑层（Hashing, Data Ordering (Linear, DAG), Ledger Storage, Cryptographic Algorithms, Sidechain, Sharding, Off-chain；另含交易模型、Merkle 树）；硬件层（CPU, GPU）。左侧竖条：链的类型影响所有层。
