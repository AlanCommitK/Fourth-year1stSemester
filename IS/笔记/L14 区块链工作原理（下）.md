## 2 区块里装了什么

### 2.1 三部分：外层头、区块头、区块体

p32："A block in a blockchain is composed of three main components: Outer header, Block header, Block body." 蓝字补了一句："The first block created in a blockchain is known as "Genesis block"."（创世块，L13 讲过。）

p33 逐一说明：

- **外层头**（outer header）："consists of block size and block identification information."——块有多大、怎样标识这个块。"outer header"不是比特币文档里的术语，课件所据的出处不明。可以看作一种对应的是比特币的区块文件（`blk*.dat`）：每个块前面存 4 字节的**网络标识**（magic number，主网是 `f9beb4d9`，用来区分主网和测试网）和 4 字节的块大小；在 P2P 网络上传块时，前面则是 24 字节的消息头（magic、命令名、长度、校验和）。考试照 p33 原话写"block size and block identification information"。
- **区块头**（block header）："consists of information such as block version, time stamp, hashing target, nonce, parent block hash, and Merkle Tree root."——6 个字段，下一小节逐个拆。
- **区块体**（block body）："All the transactions are assembled in the block body along with transaction counter."——一个交易计数，后面跟着全部交易。第一笔总是 coinbase 交易（区块里第一笔、凭空给出块矿工发奖励的交易，L13 讲过）。

![[L14 比特币区块结构.png]]

*比特币区块的三部分。区块 N 的整个区块头做两次 SHA-256（L13 讲过的哈希函数，输出 256 位），得到区块 N 的哈希，存进区块 N+1 的"前一块哈希"字段；区块体里的全部交易经 Merkle 树算出 Merkle 根，存进本块区块头。*

这张图是本节的地图，先看两条箭头：红色箭头是块与块之间的链接（[[#2.3 哈希指针：后一块存前一块区块头的哈希|2.3]]），绿色虚线是块内交易与区块头之间的链接（[[#2.4 Merkle 树：一个根概括全部交易|2.4]]）。两条链接合起来，任何一笔交易都被"拴"进了之后所有块的哈希里。

### 2.2 区块头的 6 个字段，正好 80 字节

p33 列的 6 项与比特币协议一一对应：

| 课件的叫法 | 比特币字段 | 字节 | 是什么 |
| --- | --- | --- | --- |
| block version | version | 4 | 区块格式的版本号，协议升级时用 |
| parent block hash | previous block hash | 32 | 前一块区块头的哈希，即哈希指针 |
| Merkle Tree root | merkle root | 32 | 本块全部交易的摘要，见 [[#2.4 Merkle 树：一个根概括全部交易\|2.4]] |
| time stamp | time | 4 | 出块时间，从 1970-01-01 起算的秒数 |
| hashing target | bits | 4 | 挖矿的难度目标，用 4 字节压缩表示 |
| nonce | nonce | 4 | **临时数**（nonce，number used once：常被译作"随机数"，但实际是矿工从 0 起逐个递增去试的计数器）：用来"碰"出合格哈希的那个数；实验里叫 `proof` |

两个哈希字段是 32 字节，因为 SHA-256 的输出是 256 位 = 32 字节。合计

$$
4+32+32+4+4+4=80\ \text{字节}
$$

**用比特币创世块实算核对。** 2009 年 1 月 3 日的创世块，6 个字段是：

| 字段 | 创世块的值 |
| --- | --- |
| version | 1 |
| previous block hash | 全 0（前面没有块） |
| merkle root | `4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b` |
| time | 1231006505，即 2009-01-03 18:15:05 UTC |
| bits | `1d00ffff` |
| nonce | 2083236893 |

按协议规定的格式把它们依次拼成一串字节。格式里有三处字节序要注意，任何一处不照做都算不出正确结果：

1. **4 个整数字段**（version、time、bits、nonce）按**小端序**（little-endian：低位字节在前）各写成 4 字节，例如 version 1 写成 `01 00 00 00`，不是 `00 00 00 01`。
2. **两个哈希字段**（previous block hash、merkle root）按比特币的"内部字节序"存，即把上表里显示的十六进制**按字节整体反过来**再写进去（比特币显示哈希时习惯反序，存的时候是正序）。
3. **算出的块哈希同样要反过来显示**。两次 SHA-256 的原始输出是 `6fe28c0ab6f1b372…19d6000000000000`（零在右边），按字节反序才是公认的写法。

照此拼出的字节串长度正好 80；做两次 SHA-256，反序显示，得到

`000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f`

与公认的比特币创世块哈希完全一致。

> [!example]- 可以直接运行的验算代码
> ```python
> import hashlib, struct
> merkle_hex = "4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b"
> header = (struct.pack("<I", 1)                   # version，小端
>           + bytes(32)                            # previous block hash，全 0
>           + bytes.fromhex(merkle_hex)[::-1]      # merkle root，按字节反序
>           + struct.pack("<III", 1231006505, 0x1d00ffff, 2083236893))  # time、bits、nonce，小端
> assert len(header) == 80
> raw = hashlib.sha256(hashlib.sha256(header).digest()).digest()
> print(raw[::-1].hex())   # 反序显示：000000000019d6…8ce26f
> ```

从这次实算能读出三件事：

1. p33 的字段清单准确且完整：只用这 6 个字段就复现了真实的块哈希。
2. **块自己的哈希不在块里**，是由区块头算出来的。L13 p32 图里把"Hash"画进区块头的大括号，是示意，不是存储结构。
3. 哈希开头的那串 0 来自挖矿：矿工要找一个 nonce，使区块头的哈希（反序显示后当作一个 256 位整数）**小于或等于**目标值。创世块的目标值保证开头至少有 8 个十六进制 0（见下面的选读框）；实际出现 10 个，多出的 2 个是运气（满足目标的前提下，再多两个 0 的概率约 $1/256$）。把 nonce 加 1 改成 2083236894 再算，哈希变成 `9b227a4a…`，开头一个 0 都没有，不合格。找 nonce 只能一个个试——这和实验里从 0 起逐个试 `proof` 是同一回事。4 字节的 nonce 只有 $2^{32}\approx4.3\times10^9$ 种取值，在今天的难度下几分之一秒就试完了，所以矿工还会改 coinbase 交易里一个叫 extraNonce 的字段（这会改变 Merkle 根）或改时间戳，再从 0 重试 nonce。这种只能逐个去试的计算，就是**工作量证明**（Proof of Work，PoW：用大量计算换取出块权的共识机制）的"工作量"，[[L15 区块链共识 I]] 详讲。

> [!example]- bits 怎样表示目标值，难度 1 要试多少次（选读）
> bits 的 4 个字节拆成 1 字节指数 $e$ 和 3 字节尾数 $m$，目标值
>
> $$
> T=m\times256^{\,e-3}
> $$
>
> 创世块 bits = `1d00ffff`：$e=\texttt{0x1d}=29$，$m=\texttt{0x00ffff}$，所以 $T=\texttt{0xffff}\times256^{26}$，写成 64 位十六进制是 `00000000ffff0000…0000`（前 8 位是 0）。
> 一次尝试成功（哈希 $\le T$）的概率约是 $p=T/2^{256}\approx2.328\times10^{-10}$，平均要试 $1/p\approx4.295\times10^{9}\approx2^{32}$ 次。这就是比特币"难度 1"的含义。
> 对照实验 [[Lab3-4 区块链与 PoW 的 Python 实现]]：那里要求哈希的十六进制开头有 $d$ 个 0（题面 $d=4$，平均试 $16^4=65{,}536$ 次）。"开头有 $d$ 个 0"就是"小于目标值 $16^{64-d}$"，是比特币规则的特例。难度 1 的目标值前 8 位十六进制是 0，正相当于实验的 $d=8$：$16^8=2^{32}=4{,}294{,}967{,}296$，与上面的 $4.295\times10^9$ 对得上（$T$ 比 $16^{56}$ 略小一点点，所以多出约 $6.6\times10^4$ 次）。

### 2.3 哈希指针：后一块存前一块区块头的哈希

p16 标题"Composition of a Block"，一张两块的立体图：每块从上到下 9 格——"Previous Hash"（粉色高亮）、"Height"、"Nonce"、"Confirmations"、"Merkle Root"、"Time Stamp"、"Block Version"、"TX"、"……"。一条深红箭头从图外射入左块的 Previous Hash（指向更早的块），另一条从左块引出、指向右块的 Previous Hash。

（L11 p22 也用过这张教材图，那一版少了 Time Stamp 和 Block Version 两格。）

p17 两句："Hash pointer is responsible for pointing out the previous hash."；"hash pointer can also be used to verify the integrity of the blockchain."

**哈希指针**（hash pointer）是 L13 讲过的概念：一个字段既指明前一块是哪一块，又带着前一块内容的指纹。在比特币里，"前一块的哈希"就是**前一块区块头的哈希**（[[#2.2 区块头的 6 个字段，正好 80 字节|2.2]] 那两次 SHA-256 的结果）。它为什么能"verify the integrity"（验证完整性，即确认数据没被改过）：

1. 区块头里有 Merkle 根，Merkle 根由块里的全部交易算出（下一小节）→ 改任何一笔交易，Merkle 根变；
2. Merkle 根变 → 区块头变 → 这个块的哈希变；
3. 下一块存的还是旧哈希 → 链接断开，任何人复算就能发现。要接上，就得改后面每一块，见 [[L13 区块链工作原理（上）#4.3 篡改的两种情形|L13 的实算]]。

只对 80 字节的区块头算哈希、而不是对整块算，有两个好处：轻节点只存区块头就能核对整条链的链接；矿工每试一个 nonce 只需对 80 字节做哈希，与块里有多少交易无关。实验 [[Lab3-4 区块链与 PoW 的 Python 实现]] 的区块没有区分头和体，是对整个字典（含 `data`）做 SHA-256，原理相同，只是少了 Merkle 树这一层。

> [!warning] p16 图里的两个字段不在区块里
> **"Confirmations"不可能存在块里。** 确认数是"这个块后面已经接了多少块"，等于当前链的高度减去这个块的高度再加 1，区块浏览器显示的是现算的值。块写进链的那一刻，以后会有多少块接在后面还不知道，自然存不进去。（按这个计法块本身算第 1 个确认；课件和模拟卷算确认时间时直接用"等待块数 × 出块时间"，不细究本块算不算一个。）
> **"Height"（块高，从创世块的 0 起数的编号）也不在比特币的区块头里。** 比特币从 2013 年生效的 BIP34（Bitcoin Improvement Proposal 34，第 34 号比特币改进提案）起把高度写在 coinbase 交易里；作为一般区块链的字段（美国国家标准与技术研究院 NIST 的区块链概述报告 IR 8202 列有 block height）可以接受。
> 图里还把"TX"和头部字段画在同一列，看不出头和体的分界。p16 与 p33 冲突时**以 p33 为准**：区块头只有 version、previous block hash、merkle root、time stamp、hashing target、nonce 六项。

### 2.4 Merkle 树：一个根概括全部交易

p18 两句："Using Merkle tree can verify the set of all transactions quickly within a block."；"Merkle Tree is a binary tree used to represent transactions in a block."

p19 是定义（课件原文，粗体是课件的红字）：

> "For each transaction, a **separate hash value** is calculated. Then, the two hash values are combined to generate **a new hash going upward** toward the root. **Then at the root, all the hash values are combined to create a new hash value**. This hash value is then used for integrity and verification purpose. Now, if **this hash value has been modified**, it means, **some transactions** within the block have been modified."
> "Merkle Tree is a binary tree used to represent transactions in a block. Merkle root is known as the root of the Merkle Tree wherein each leaf is labeled as hash code of the transaction. The hash code of two children is combined together as label of the non-leaf node."

整理成构造规则。**Merkle 树**（Merkle tree，以密码学家 Ralph Merkle 命名，他 1979 年提出这种哈希树，常被引用的是他 1987 年的论文）是一棵**二叉树**（binary tree：每个上层节点恰好有两个子节点）：

1. **叶子**：每笔交易各算一个哈希。
2. **向上合并**：相邻两个哈希**首尾拼接后再哈希**一次，得到上一层的一个节点。
3. 一层层往上，直到只剩一个，叫 **Merkle 根**（Merkle root），写进区块头。

比特币的块哈希、交易标识和 Merkle 树都用两次 SHA-256，下面记 $H(x)=\text{SHA-256}(\text{SHA-256}(x))$，$\Vert$ 是字节拼接。取 4 笔示意交易实算：

| 层 | 节点 | 怎么算 | 值 |
| --- | --- | --- | --- |
| 叶 | $h_0$ | $H(T_0)$，$T_0$ = `Alice->Bob:5` | `af5776d147c1fd84…` |
| 叶 | $h_1$ | $H(T_1)$，$T_1$ = `Bob->Carol:2` | `0bcd6c394e21b6a9…` |
| 叶 | $h_2$ | $H(T_2)$，$T_2$ = `Carol->Dave:1` | `0e2c654dc8fef9a4…` |
| 叶 | $h_3$ | $H(T_3)$，$T_3$ = `Dave->Eve:3` | `e0a60060b17b5a21…` |
| 中 | $h_{01}$ | $H(h_0\Vert h_1)$ | `635ac9cd45227b2c…` |
| 中 | $h_{23}$ | $H(h_2\Vert h_3)$ | `4ea48438f6104040…` |
| 根 | $R$ | $H(h_{01}\Vert h_{23})$ | `97b4c43f10c7e4e3…` |

（表中示意值按 SHA-256 输出的原始字节顺序显示，与区块浏览器的反序显示相反，不要拿去和 [[#2.2 区块头的 6 个字段，正好 80 字节|2.2]] 的创世块 merkle root 对比。）

![[L14 Merkle 树与证明路径.png]]

*四笔交易的 Merkle 树。红色是 $T_2$ 到根的路径，绿色是验证 $T_2$ 时需要别人提供的兄弟节点（[[#2.5 Merkle 证明：轻节点为什么只存头就够|2.5]] 用到）。*

**篡改检测**（p19 最后一句"if this hash value has been modified, it means, some transactions within the block have been modified"）：把 $T_2$ 改成 `Carol->Dave:9`，重算：

- $h_2$ 变成 `26b1c136…`；
- $h_{23}=H(h_2\Vert h_3)$ 变成 `afbdab29…`；
- $R=H(h_{01}\Vert h_{23})$ 变成 `d1aa7414…`，与原来的 `97b4c43f…` 不同。

变化只沿图里红色路径往上传，$h_0$、$h_1$、$h_{01}$、$h_3$ 都不变；但根一定变。根在区块头里，于是接上 [[#2.3 哈希指针：后一块存前一块区块头的哈希|2.3]] 的因果链：区块头变 → 块哈希变 → 下一块的链接断。

> [!note] p19"at the root, all the hash values are combined"说得不准
> 根并不是把所有哈希一起合并，而是只把它的两个子节点拼接后再哈希，和其他非叶节点的算法一样。课件也没说用哪种哈希函数（比特币是两次 SHA-256）、交易个数为奇数时怎么办。

> [!example]- 交易数为奇数时：复制最后一个凑成对（课件外）
> 比特币的规则：某一层的节点数是奇数时，把这一层最后一个哈希复制一份，与自己配对。取上表前 3 笔交易：
> - 第一层：$h_0,h_1,h_2$ 三个，$h_2$ 落单，于是 $h_{22}=H(h_2\Vert h_2)=$ `92795826…`；
> - 根 $=H(h_{01}\Vert h_{22})=$ `6b53aaec…`。

### 2.5 Merkle 证明：轻节点为什么只存头就够

p18 说 Merkle 树能"quickly"验证交易。快在哪里，要分清两件事：

- 只想检测"这个块里有没有任何一笔交易被改过"，根本用不着树：把全部交易拼起来算一个哈希，也能做到。
- Merkle 树真正的本事是：**不拿到其他交易，也能证明某一笔交易在这个块里。**

例：一个轻节点只存了区块头（因而知道 $R$），想确认 $T_2$ 确实被打包进了这个块。它向全节点要两个兄弟哈希——$T_2$ 的兄弟 $h_3$、$h_{23}$ 的兄弟 $h_{01}$（图中绿色）——以及每个兄弟在左还是在右（因为 $H(a\Vert b)\neq H(b\Vert a)$，拼接顺序错了就算不对）。左右位置等价于 $T_2$ 在块里的序号：2 写成二进制是 10，从低位读起，第一层 $T_2$ 在左、兄弟在右，第二层 $h_{23}$ 在右、兄弟在左。然后自己沿红色路径算：

$$
R\ \overset{?}{=}\ H\big(h_{01}\ \Vert\ H(H(T_2)\ \Vert\ h_3)\big)
$$

实算等式成立。若全节点给的是假值，或 $T_2$ 根本不在块里，算出来的根就对不上区块头里的 $R$——由于哈希抗第二原像与抗碰撞，造不出能凑出正确根的假兄弟。

证明要几个哈希：树每高一层，路径上多一个兄弟，$n$ 笔交易的树高 $\lceil\log_2 n\rceil$（$\lceil x\rceil$ 表示上取整：不小于 $x$ 的最小整数），所以只要 $\lceil\log_2 n\rceil$ 个 32 字节的哈希，外加同样多位的左右位置信息：

| 块内交易数 $n$ | 证明所需哈希数 | 证明大小 | 对比：全部叶哈希 $32n$ 字节 |
| --- | --- | --- | --- |
| 4 | 2 | 64 B | 128 B |
| 1,000 | 10 | 320 B | 32,000 B |
| 4,000 | 12 | 384 B | 128,000 B |
| 75,000 | 17 | 544 B | 2,400,000 B |
| 1,000,000 | 20 | 640 B | 32,000,000 B |

（75,000 是 [[#6.3 吞吐量受什么限制|6.3]] 模拟卷那条链每块的交易数。）交易数涨到一百万，证明也只有 640 字节。这就是 [[L13 区块链工作原理（上）#3.3 轻节点：只存区块头|轻节点]]只存 80 字节的区块头也能工作的原因（比特币白皮书第 8 节的 SPV）。

> [!warning] Merkle 证明证的是"在块里"，不是"合法"
> 误：轻节点用 Merkle 证明验证了交易，所以它和全节点一样安全。
> 正：Merkle 证明只说明"这笔交易被写进了这个块"。这笔交易花的钱以前有没有花过、签名对不对，轻节点没法自己查，只能相信"被多数算力接上了后续块的块里不会有非法交易"。独立验证合法性的仍然只有全节点。

## 3 治理：谁拥有、谁能写、保不保密

课件把 p16–p22 都放在"Blockchain Governance System"标题下。**治理**（governance）在这里指：链归谁、谁有权往上写、谁能看到数据。区块组成已在第 2 节讲完，本节是 p20–p22。

### 3.1 谁拥有区块链

p20："In terms of deployment and involvement of companies, different companies can operate in a consortium blockchain." "However, if there is only a single organization involved, then it can be considered as a private blockchain."

多家公司共同运营的是联盟链，只有一家的是私有链。p20 没说公有链，按 [[L13 区块链工作原理（上）#1.1 三类链与两种许可|三类链的定义]]，公有链没有所有者，谁都能参与。

### 3.2 谁能修改账本

p21："In terms of ledger modification, blockchain can be classified as permissionless and permissioned." "In permissionless blockchain, anyone can modify the ledger." "In permissioned blockchain, restricted number of nodes can make modification in the ledger."

> [!warning] p21 的"modify"应理解为写入新块
> 误：无许可链上"任何人都能修改账本"。
> 正：正常途径只能往后**追加**新块。已有的记录不能被悄悄修改：一改就会被发现（篡改可检测，tamper-evident，[[#2.3 哈希指针：后一块存前一块区块头的哈希|2.3]]），PoW 链上还要重做其后所有块的工作量（篡改代价高，tamper-resistant，见 [[L13 区块链工作原理（上）#4.3 篡改的两种情形|L13 的篡改两种情形]]）。p21 的"modify"指的是**写入**：无许可链上任何人都能提交交易、参与竞争出块，新块要经共识被接受；许可链上只有被授权的节点能出块。

### 3.3 机密性

p22：

- "Public blockchain systems do not provide confidentiality except the blockchain user and their actual identities are not disclosed to the general public using pseudonymity."
- "Consortium and private blockchain provide more confidentiality to the blockchain users, however, blockchain nodes need more trust in such an environment, and **the identity of the nodes should be known** within the network."（粗体为课件红字）

两个词要分开：

- **机密性**（confidentiality）：信息只让被授权的人看到，信息安全三目标之一（[[L1 信息安全基础]]）。公有链上每一笔交易的金额、收付地址对全世界公开，谈不上机密性。
- **假名性**（pseudonymity）：用一个不直接写真名的地址代替身份。它保护的只是"这个地址是谁"，而且并不牢靠——同一个人的多个地址常在交易里一起出现，研究者靠这种关联做**地址聚类**（address clustering：把可能属于同一人的多个地址归成一组）就能把大量比特币地址和真实身份对上（Meiklejohn 等，2013）。

许可链的取舍是：节点身份已知（比如 Hyperledger Fabric——Linux 基金会主导的许可链平台，常用于联盟场景——给每个成员发 [[L8 数字签名、证书与 PKI]] 里讲的数字证书），可以只让授权方看到数据，机密性更好；代价是参与者必须信任发证的机构与彼此——"need more trust"。

### 3.4 三类链的治理对照

| | 公有链 | 联盟链 | 私有链 |
| --- | --- | --- | --- |
| 谁拥有（p20） | 无单一所有者 | 多家公司共同运营 | 单一组织 |
| 谁能写入（p21） | 任何人（permissionless） | 受限的节点（permissioned） | 受限的节点（permissioned） |
| 机密性（p22） | 不提供，只有假名性 | 更高，节点身份须已知 | 更高，节点身份须已知 |

### 4.3 比特币

**要点**（p28）："Bitcoin is one of the famous first publicly available cryptocurrency platforms that use the concept of blockchain."

- "Consensus mechanism uses Proof-of-Work (PoW)"——对。
- "Partially supports smart contracts using UTXO"——说法不准。**UTXO**（Unspent Transaction Output，未花费交易输出）是比特币的记账方式：每笔交易消耗掉以前交易的若干个"输出"，再产生新的输出；一个人的"余额"就是所有能被他的私钥解锁、还没被花掉的输出之和。比特币有限的可编程性来自附在每个输出上的一小段 **Bitcoin Script**（比特币脚本：规定"满足什么条件才能花这笔钱"的简单语言，故意设计成不能写循环），不是来自 UTXO 本身。
- "Operates over P2P network architecture"——对，即 L13 讲的对等网络。
- "Some nodes can keep the copy of the ledger."——含糊；准确说法是全节点存完整账本，轻节点只存区块头。
- "Provides a hard code list of Domain Name Server (DNS) – resist DoS attacks."——客户端里硬编码的是 **DNS 种子**（[[L13 区块链工作原理（上）#2.2 至少要有几个直接相连的邻居|L13 讲过]]：查询后能拿到一批在线节点地址的域名），用途是新节点启动时找到第一批邻居，不是"Domain Name Server"；"抵抗 DoS 攻击"（denial of service，拒绝服务攻击：用海量请求把服务压垮）一说找不到依据。
- "Virtual crypto coins BTC are used"——对。

**靠什么在没有中心机构的情况下建立信任**（p29，八项）：

| 特征 | 在比特币里起什么作用 |
| --- | --- |
| Cryptography（密码学） | 哈希与签名是下面几项的基础 |
| P2P Network Architecture | 没有中心服务器，无单点可攻 |
| Hashing Algorithms | 串链、Merkle 根、挖矿 |
| Public/Private Key Encryption | 课件写 encryption 不准：比特币**不加密**任何交易，公私钥用于**签名**（ECDSA，Elliptic Curve Digital Signature Algorithm，椭圆曲线数字签名算法；2021 年 Taproot 升级（比特币的一次协议升级）后另可用 Schnorr 签名，也是一种基于椭圆曲线的签名算法） |
| Distributed Storage | 每个全节点存一份完整账本 |
| Logically Centralized | 物理上分散在成千上万台机器上，逻辑上只有一本账：诚实节点最终都收敛到同一条链 |
| Consensus Algorithm | PoW 决定谁出下一块 |
| Time Stamping of Transactions | 每个区块头带时间戳，交易先后有据可查 |

**比特币的最小单位**（p30）："The smallest amount of BTC that can be transferred is 0.00000001 BTC, which is also known as "Satoshi"."

$$
1\ \text{Satoshi}=\frac{1}{100{,}000{,}000}\ \text{BTC}=10^{-8}\ \text{BTC}
$$

名字来自比特币的创造者中本聪（Satoshi Nakamoto）。比特币协议内部记金额就以聪为整数单位，避免小数误差。例：0.0015 BTC $=0.0015\times10^8=150{,}000$ 聪；比特币总量上限 2100 万 BTC $=2.1\times10^{15}$ 聪。p30 还说 BTC 既可用来转移价值，也作为挖矿奖励发给矿工（就是 coinbase 交易）。

**比特币的工作过程**（p31）七步，与 L13 的 13 步对照：

| p31 原文 | 对应 L13 的步骤 |
| --- | --- |
| 1. "A participating node send a transaction to neighboring nodes" | ④ 广播交易 |
| 2. "Neighboring nodes check this transaction" | ⑤ 验证交易 |
| 3. "All the nodes including miners add this transaction to the unverified transaction pool." | ⑥ 进交易池 |
| 4. "Miner node gathers few transactions and starts mining the block" | ⑦ 组块、⑧ 挖矿 |
| 5. "Informs a block (including set of transactions) to the whole network." | ⑩ 加块、⑪ 广播（原文缺主语：是挖到块的矿工广播） |
| 6. "Full nodes (including miners) check different fields of the block and its validity." | ⑨ 验证区块 |
| 7. "The nodes add correct block to their copy of the ledger." | ⑫ 加入本地副本 |

两处值得注意：第 6 步明说**全节点**检查区块，再次说明 p3 表里全节点"Transaction validation"为"–"是错的；验证区块放在广播之后，意思是收到块的每个节点都要独立检查（L13 第 9 步只说了"Block validation is carried out"，没说谁做）。p31 第 3 步把交易池叫"unverified transaction pool"，意思是池里的交易虽已通过检查，还没被写进块、没得到区块确认。

区块的组成（p32–p33）已在 [[#2.1 三部分：外层头、区块头、区块体|第 2 节]]讲过。

### 4.4 以太坊与它的两类账户

**要点**（p34）：

- "Pubilc available cryptocurrency. (Ethers are used as cryptocurrency. )"——以太坊的币叫 **Ether**（以太币，ETH）。
- "Incorporates business logic to blockchain network in the form of smart contract."——以太坊的核心：链上可以部署任意的智能合约。
- "Proof-of-Work (PoW) variant of consensus algorithm named as Ethash (Ethereum 2.0 uses PoS)"——已过时。以太坊早期用 PoW 的一个变体 Ethash，**2022 年 9 月 15 日"合并"（The Merge）之后全面改为 PoS**（Proof of Stake，权益证明：按持有并锁定的币量选出块者，见 [[L15 区块链共识 I]]），Ethash 不再使用；以太坊基金会也不再用"Ethereum 2.0"这个名字。
- "Participating node needs to install/host Ethereum Virtual Machine (EVM) to execute smart contracts."——**EVM**（Ethereum Virtual Machine，以太坊虚拟机）：每个节点上都运行的同一个执行环境，合约编译成它的**字节码**（bytecode：给虚拟机执行的低级指令序列），在每个节点上以完全相同的方式执行。
- "Built on top of P2P network and requires virtual P2p (Vp2p) wire protocol."——协议名写错了：以太坊节点间的通信协议叫 **devp2p**（写作 ÐΞVp2p，Ð 取自 Dev），不是"virtual"。

**账户**（p35）："In Ethereum blockchain, there are three types of users"，列了 Contract Account (CA)、Miners、Externally Owned Account (EOA)。这一页有错，先给正确版本。以太坊官方文档（ethereum.org，"Ethereum accounts"）的说法是：**以太坊只有两类账户。**

| | 外部账户 EOA | 合约账户 |
| --- | --- | --- |
| 英文 | Externally-owned account | Contract account |
| 由谁控制 | "controlled by anyone with the private keys"：持有私钥的人 | "a smart contract deployed to the network, controlled by code"：合约代码 |
| 有没有私钥 | 有一对公私钥，地址由公钥得到（公钥的 Keccak-256 哈希值的后 20 字节） | 没有私钥 |
| 能否主动发起交易 | "Can initiate transactions" | 不能。"Can only send messages in response to receiving a transaction"：只能在收到一笔交易后作为响应去调用别的账户 |
| 创建的代价 | "Creating an account costs nothing" | 部署合约要付费，因为占用了网络的存储 |
| 典型用途 | 普通用户的钱包 | 一份部署好的合约，如代币、拍卖、交易所 |

两类账户都能持有以太币。（课外：2025 年 5 月的 Pectra 升级引入 EIP-7702（Ethereum Improvement Proposal 7702，第 7702 号以太坊改进提案），允许 EOA 把自己的执行逻辑委托给某个合约代码，ethereum.org 的账户页因此加了"unless the account has delegated…"一类限定语。账户仍是两类，考试答法不变。）以太坊因此是**账户模型**（每个账户直接记一个余额），和比特币的 UTXO 模型不同（L13 六层的数据组织层提到的"transaction models"就是这对区别）。

这样看一次合约调用：用户的 EOA 用私钥签一笔交易发给合约账户 → 合约代码在每个节点的 EVM 里执行 → 执行中合约可以再去调用别的合约。整条调用链的源头一定是某个 EOA 发起的交易。

> [!warning] 课件 p35 的两处错误
> **把合约账户说成普通用户。** 课件原文"Contract Account (CA), which are normal users and can make transactions among each other"。正好说反了：普通用户用的是 EOA；合约账户由代码控制、没有私钥，不能主动发起交易，只能响应收到的交易。
> **把矿工列为一类账户。** 矿工（The Merge 之后叫验证者 validator）是**节点的角色**（[[L13 区块链工作原理（上）#3.4 矿工节点：唯一能往链上加块的|L13 的节点分类]]），不是账户类型；矿工收奖励用的也是一个普通的 EOA。
> 课件对 EOA 的描述是对的："can perform transaction to another EOA. EOA can also call the function of CA and they can also make a new smart contract."
> 考试问以太坊账户，按正确定义答两类：EOA（私钥控制、能发起交易）与合约账户（代码控制、只能响应）。

## 5 智能合约：确定性与非确定性

p36 是大纲过渡页，高亮第四项"Properties of Blockchain System"，第 5–7 节都属于这一项。p37–p38（课件页眉写"Blockchain Platforms"，内容属于"Properties of Blockchain System"）把智能合约分两类：

| | 确定性智能合约 | 非确定性智能合约 |
| --- | --- | --- |
| 英文 | Deterministic smart contracts | Non-deterministic smart contracts |
| 课件定义 | "The execution of smart contract is not dependent upon external data or event." | "The execution of smart contract is dependent upon external data (also called as oracles)." |
| 例子 | 代币转账：A 的余额减 5、B 的加 5，所需数据都在链上 | 航班延误险：航班晚点两小时就自动赔付，"晚点了没有"在链外 |

p38 底部蓝字："Non-deterministic smart contract opened the door of new and innovative applications and business models."——能读取真实世界的数据，合约才能做保险、供应链、博彩这类业务。

为什么要分这两类：智能合约在**每个节点上都执行一遍**，各节点必须得到一模一样的结果，否则对"执行后账本是什么样"就无法达成共识。只依赖链上数据的合约，输入相同、结果必然相同。如果合约在执行时让每个节点自己去网上查航班状态，节点查询的时刻不同、网站返回的内容可能不同，结果就会分叉。

解决办法是**预言机**（oracle）：一个把链外数据写上链的机制或服务。它先把"航班 CA123 晚点 135 分钟"作为一笔交易写进链里，所有节点执行合约时读的都是链上同一份数据，执行本身又变回确定的。课件说外部数据"also called as oracles"不准确：预言机是送数据的机制，不是数据本身。代价也随之而来：合约的结果只和预言机一样可信，预言机成了新的信任点。

## 6 可扩展性与交易容量

### 6.1 可扩展性的三个维度

**可扩展性**（scalability）：系统规模变大时性能能否跟上。p39 从三个方向问：

- "How much scalable the blockchain system is when we increase the number of blockchain nodes?"——**节点**变多：每条消息要传给更多节点，传播变慢；
- "How blockchain system behave when there is an increase in number of transactions?"——**交易**变多：每块装不下，交易在池里排队；
- "How blockchain system behaves when the size of the ledger increases in terms of storage?"——**账本**变大：存储负担越来越重。

### 6.2 存储：账本只增不减

p40："Basically, each blockchain keeps the copy of the complete ledger."（应为"each blockchain node"）"With the passage of time, new blocks are adding, and the size of the ledger keeps growing." "When applying blockchain to certain communication networks in which the nodes **do not have high storage capacity**, keeping the full copy of the ledger is problematic."

因果很直接：区块链只追加、不删除，所以账本只会越来越大；每个全节点都存一整份，存储需求随时间线性增长。这对传感器、手机、车载设备这类存储有限的无线节点（课程最后几讲 L18–L20 的应用场景）是硬约束。轻节点（只存区块头）是一种缓解。

### 6.3 吞吐量受什么限制

p41："The performance of blockchain system can be measured in terms of number of transactions handled per second by the blockchain."——衡量区块链性能的指标是**吞吐量**（throughput：每秒处理的交易数，单位 Tx/s，也写作 TPS）。p41 列了三个限制因素，p42 给了对应的三条对策：

| p41 限制因素 | p42 对策 |
| --- | --- |
| 1. "Transactions included in each block" | "The higher the number of transactions included in each block, the higher the throughput." |
| 2. "Transaction speed" | "Efficient and quick responding consensus algorithms are required." |
| 3. "The interarrival time of blocks" | "The fast interarrival time of blocks is needed" |

**interarrival time of blocks**（出块间隔：相邻两个块之间的平均时间，也叫 block time）。

这三条在下一讲 [[L15 区块链共识 I]] 会变成一个公式。先看它为什么长这样：每秒的交易数 = 每块装几笔 × 每秒出几块，而每块装几笔 = 块的容量 ÷ 每笔交易的大小，每秒出几块 = 1 ÷ 出块间隔。于是

$$
\text{Throughput}=\frac{\text{Block Size}}{\text{Tx Size}}\times\frac{1}{\text{Block Time}}=\frac{\text{Block Size}}{\text{Tx Size}\times\text{Block Time}}
$$

对照 p42：第 1 条是让分子那一项（每块交易数）变大；第 2 条（共识要快）作用在分母——共识越快，出块就能越快，Block Time 才能缩短；第 3 条直接要求缩短分母里的 Block Time。（与 [[L15 区块链共识 I]] 的说法一致。）p41 第 2 项的"Transaction speed"本身不是公式里的量，它由共识的快慢决定，p42 给的对策就是加快共识。

**算一个例子**（模拟卷 Q3(b)(iii)）："Suppose a blockchain network has a block size of 6 MBytes, transaction size of 80 Bytes, Block time is 200 seconds and it requires to wait for 20 blocks to confirm any new block. Calculate the average block confirmation time and transaction per second (throughput) of this blockchain network. [3 marks]"

1. 每块交易数：$6\times10^6\ \text{B}\div80\ \text{B}=75{,}000$ 笔（课件 L15 的例题按 $1\ \text{MB}=10^6\ \text{B}$ 算，这里同样取 $10^6$）。
2. 吞吐量：$75{,}000\div200\ \text{s}=375\ \text{Tx/s}$。
3. 平均确认时间：$20\times200\ \text{s}=4000\ \text{s}$（"确认"在这里指等后面 20 个块，见 [[L13 区块链工作原理（上）#5.3 传播与确认：第 11–13 步|L13 的"确认"两义]]）。

> [!warning] 模拟卷参考答案的 37.5 Tx/s 是错的
> 参考答案写"Transaction Throughput = 6 (M Bytes) / (80 (Bytes) × 200 (seconds)) = 37.5 Tx/second"。公式是对的，数算错了：$6\times10^6/(80\times200)=6\times10^6/16{,}000=375$。反推 37.5 要求块只有 $37.5\times80\times200=600{,}000$ 字节 = 0.6 MB，多除了一个 10。按 $1\ \text{MB}=2^{20}\ \text{B}$ 算是 393.216 Tx/s，也不是 37.5。
> 口径依据：L15 p53 的例题按 $10^6$ 代入，它的结果 200 Tx/s 同样算错了（应为 20 Tx/s），但 $10^6$ 的口径是明确的，见 [[L15 区块链共识 I]]。
> 考场写法：先写"taking 1 MB = $10^6$ bytes"，再写公式、代数、得 375 Tx/s——参考答案三个给分点（公式、吞吐量数值、确认时间）都能拿到。

三条对策的效果可以直接从公式读出：块容量翻倍（12 MB）或出块间隔减半（100 s），吞吐量都翻倍到 750 Tx/s。作为参照，比特币取 1 MB 块、每笔约 250 B、600 s 出一块，$10^6/(250\times600)\approx6.67$ Tx/s，就是常说的"比特币每秒约 7 笔"。

> [!note] 为什么不能把块无限加大、间隔无限缩短（课件外）
> 块越大，传遍全网越慢；间隔越短，两个矿工几乎同时出块、链暂时分叉的机会越多，分叉越多，作废的块越多，攻击者也越容易钻空子。块大还意味着每个全节点要更多存储和带宽，能跑全节点的人变少，网络就趋向中心化。去中心化、安全、可扩展三者难以兼得，常被称为**可扩展性三难**（scalability trilemma）。所以 p43 接着提出侧链、链下和分片：不在一条链上硬挤，而是换一种结构。

### 6.4 侧链与链下交易

p42 的三条之后，p43 补了第 4、5 条："Another possible way to increase the transaction capacity is to offload the transactions from the main blockchain to the **side chain**." "**Sharding** is an important concept in blockchain which is proposed to handle transaction capacity, bottleneck of blockchain systems."（粗体为课件红字。）第 5 条分片放到下一小节。

p44 展开第 4 条（粗体为课件红字）："Another possible way to increase the transaction capacity is to offload the transactions from the main blockchain to the **side chain**. This process is known as **off-chain transactions**. Researchers also explored the idea to store only **the hashes in the main blockchain** while **other data** need to store in off-chain solutions. In this manner, the overall storage requirement of keeping the ledger **will not surpass** the storage requirements of light weight nodes."

p44 说了两个想法：

**一、把交易挪到主链之外处理。** 课件把"转移到侧链"叫作"off-chain transactions"，用的是**广义的链下**（off-chain：凡是不在主链上处理的交易都算）口径；L15 p54 举链下方案时也写"Sidechains, Payment Channels, etc."，两讲一致。广义链下里有两种机制不同的做法：

- **侧链**（sidechain）：另一条独立运行的区块链，通过**双向锚定**（two-way peg：在主链上锁定一笔币，就在侧链上放出等量的币，反之亦然）与主链互通。大量交易在侧链上完成，主链只处理锁定和释放。侧链有自己的区块和共识。
- **支付通道**（payment channel），即**狭义的链下交易**：交易根本不上任何链。典型是比特币的**闪电网络**（Lightning Network）：两人在主链上开一个支付通道（锁定一笔钱），之后在通道里互相签名来回付款任意多次，只有关闭通道时才把最终结果写回主链。成千上万笔支付最后只占主链两笔交易。

**二、主链只存哈希，数据存在链外。** 原始数据（文件、图片）放在别处，主链只存它的哈希。由 L13 讲的哈希性质，哈希就是数据的指纹：日后有人拿出数据，算一下哈希与链上的对比，就知道数据有没有被改过。这样主链上每条记录只占 32 字节。课件说这样账本的存储"will not surpass"轻节点的需求，是夸大：账本仍随时间增长，只是长得慢得多。

### 6.5 分片

p45（粗体为课件红字）："In **sharding**, blockchain nodes are divided into multiple groups (shards) and each group (shard) is responsible to handle a certain amount of transactions **in parallel**. However, in sharding system, it is necessary to consider how all the blockchain nodes **keep the copy** of the complete ledger. Additionally, it is also important to consider how different blockchain nodes (groups) **communicate with each other**."

**分片**（sharding）这个词借自数据库：把一张太大的表按某种规则切成几块，分放到不同服务器上。区块链里的做法是：把全网节点分成若干组，每组叫一个**分片**（shard），每个分片只处理分给它的那一部分交易，各分片**同时**工作。

为什么能提高容量：不分片时，全网每个节点都要处理每一笔交易，加再多节点，吞吐量也不变——多出来的节点只是在重复同样的工作。分片后，$k$ 个分片各自出块，理想情况下吞吐量约为单链的 $k$ 倍。例如 [[#6.3 吞吐量受什么限制|6.3]] 那条 375 Tx/s 的链分成 4 个分片，理想上可到 $4\times375=1500$ Tx/s（这是不计分片间通信开销的上限）。而且节点越多，能分的片越多，吞吐量随网络规模一起增长，这就是"可扩展"的本义。

p45 提出两个要考虑的问题：

- **账本副本**（"keep the copy of the complete ledger"）：每个节点只处理本分片的交易，它手里就只有一部分账本；全网的完整账本怎样保存、怎样核对，要专门设计。
- **分片之间的通信**（"communicate with each other"）：一笔交易的付款方在分片 1、收款方在分片 2，两个分片必须协调，保证这笔交易要么两边都生效、要么都不生效，这叫**跨分片交易**（cross-shard transaction）；"要么都生效、要么都不生效"这一要求叫**原子性**（atomicity）。

> [!note] 课外补充：分片真正的难点
> p45 说"要考虑所有节点怎样保存完整账本"，与分片的设计初衷相反：分片的目的正是让每个节点**不再**存、不再处理全部交易。研究文献里分片的主要难点是两个：跨分片交易的原子性（上面第二点）与各分片之间的一致性；以及**单分片被攻占**——每个分片的节点只有全网的一小部分，攻击者不必控制全网，只要集中力量控制一个分片就能在那里作恶，所以要定期随机打乱节点在分片间的分配。考试照课件写"账本副本 + 分片间通信"两点即可。

**模拟卷 Q3(b)(v)**："Explain the advantages of sharing. [2 marks]"（sharing 是 sharding 的笔误。）参考答案任答两项、每项 1 分：

> [!example] Q3(b)(v) 答法
> Sharding divides the nodes into groups (shards); each shard processes its own share of transactions in parallel. Advantages:
> - **High scalability**: adding nodes allows more shards, so throughput grows with the size of the network instead of staying fixed.
> - **Greater transaction capacity**: shards process transactions in parallel, so the total throughput is roughly the sum over all shards, removing the transaction-capacity bottleneck.
> - **Low cost**: each node only processes and stores the transactions of its own shard, which reduces its computation, storage and bandwidth cost.
>
> 前两条有课件原文依据（p45"in parallel"、p43"handle transaction capacity, bottleneck"、p39 的可扩展性语境）；"low cost"课件没有出现，是参考答案额外给的，写的时候附上一句理由更稳。

## 7 互操作性

### 7.1 为什么需要互操作

p46："Implement and operate multiple distributed ledgers." "Ledgers can be developed by different organizations and thus designed for specific purposes." "Interoperability is required among ledgers to share information and talk with each other."

**互操作性**（interoperability）：不同系统之间交换信息、协同工作的能力。现实中有许多条链，由不同组织为不同目的建造；一家银行的联盟链和一条供应链的链要对账，比特币持有者想换成以太币，都需要链与链之间能"说话"。p47 指出互操作在编程语言和数据库领域早就存在，并说交易所（exchanges）是在不同账本之间交换加密货币的一种办法——它能用，但交易所本身是一个中心化的第三方，用户要信任它，这正是区块链想去掉的东西。

### 7.2 影响互操作的因素

p48 列了八项（"Important factors of Interoperability"），每项都是两条链之间可能"对不上"的地方：

| 因素 | 为什么影响互操作 |
| --- | --- |
| Smart Contract | 两条链的合约语言与执行环境不同，一边的合约无法直接调用另一边 |
| Exchange | 资产怎样在两条链之间兑换 |
| Consensus Protocols | 共识不同，"一个块什么时候算定下来"的标准也不同 |
| Generation of blockchain systems | 第一代（只有交易）、第二代（有智能合约）等不同代的链能力不同 |
| Transaction Speed | 一边几秒出块、一边十分钟出块，跨链操作要等慢的那一边 |
| Semantic | 语义：同一个字段在两条链上是否表示同一个意思 |
| Transaction Fees | 两边各收各的手续费，计价单位也不同 |
| Tokens | 各链的代币不同，跨链要处理换算与锁定 |

### 7.3 实现互操作的六种途径

p49"How is blockchain interoperability achieved?"列了六项，课件只列名字、没有解释（右侧一张星形图：中心"Interoperable blockchain"，四周 Supply chain、Chain 1、Private bank、Chain 2 用双向箭头连到中心，表示交换数据与资产）：

- **Sidechains**（侧链）：[[#6.4 侧链与链下交易|6.4]] 的双向锚定，主链与侧链之间就互通了。
- **Notary schemes**（公证人方案）：由一个或一组受信任的"公证人"监听链 A 上的事件，再在链 B 上确认或执行。简单，但要信任公证人。
- **Oracles**（预言机）：[[#5 智能合约：确定性与非确定性|第 5 节]]的预言机把一条链上发生的事当作"外部数据"送到另一条链。
- **Blockchain routers**（区块链路由器）：在多条链之间转发跨链消息的中继，像互联网里在不同网络之间转发数据包的路由器。
- **Industrial solutions**（工业方案）：课件没有解释，推测指 Polkadot、Cosmos 这类专门做跨链的项目（两者都让多条链经一个中心枢纽互通）。
- **Hashed TimeLocks**：标准名称是**哈希时间锁合约**（HTLC，Hashed Timelock Contract），见下面的例子。

> [!example]- 哈希时间锁怎样让两条链上的交换"要么都成、要么都不成"（课件外）
> 场景：Alice 在链 A 上有币，想换 Bob 在链 B 上的币，两人互不信任，也不想用交易所。
> 1. Alice 随机选一个秘密数 $s$，算出它的哈希 $h=H(s)$，只公开 $h$。
> 2. Alice 在链 A 上锁定她的币，条件是：谁能出示一个哈希等于 $h$ 的数，谁就能取走；若 48 小时内没人取，币退回 Alice。
> 3. Bob 看到后，在链 B 上用**同一个** $h$ 锁定他的币：谁出示 $h$ 的原像就能取走；若 24 小时内没人取，退回 Bob。
> 4. Alice 在链 B 上出示 $s$，取走 Bob 的币。这一步让 $s$ 公开在链 B 上。
> 5. Bob 从链 B 上读到 $s$，拿去链 A 取走 Alice 的币。
>
> 为什么安全：哈希锁靠哈希函数的单向性——只知道 $h$ 的人算不出 $s$，所以 Bob 无法抢先取 Alice 的币；时间锁保证任何一方中途放弃，对方的币都能按时退回。Bob 的期限比 Alice 短，是为了让 Bob 在 Alice 出示 $s$ 之后还有时间去链 A 取款。

p50 小结列了本讲四节：General Process、Governance System、Platforms、Properties。

## 本讲速记

- p3–p14 重复 L13（节点职能表、三套分类、六层、13 步），见 [[L13 区块链工作原理（上）]]。
- **区块三部分**（p32–p33）：外层头（"block size and block identification information"；课件术语，比特币存盘格式里对应 magic + 块大小）；**区块头**（version、previous/parent block hash、Merkle root、time stamp、hashing target、nonce）；区块体（交易计数 + 全部交易）。区块头 $4+32+32+4+4+4=80$ 字节。创世块：整数小端、哈希字段按字节反序拼成 80 字节，两次 SHA-256 后反序显示 = `000000000019d6689c…8ce26f`。挖矿条件：哈希 $\le$ 目标值；nonce 对应实验的 `proof`，难度 1 相当于实验 $d=8$（约 $2^{32}$ 次）。**块自己的哈希不在块里**，由头算出。
- **哈希指针**（p16–p17）：后一块存前一块区块头的哈希，指向前一块并可验证完整性。p16 图里的 Height（不在比特币区块头里）、Confirmations（现算的，不可能存储）不是区块头字段；与 p33 冲突时以 p33 为准。
- **Merkle 树**（p18–p19）：二叉树；叶 = 每笔交易的哈希；上层 = 两个子哈希拼接后再哈希；根写进区块头。改任一交易 → 根变 → 头变 → 块哈希变 → 下一块链接断。奇数个则复制最后一个。
- **Merkle 证明**：证明某笔交易在块里只需 $\lceil\log_2 n\rceil$ 个兄弟哈希及其左右位置（100 万笔交易只要 20 个、640 字节）→ 轻节点只存头也能用（SPV）。证的是"在块里"，不是"合法"。
- **治理**（p20–p22）：多家公司运营 = 联盟链，单一组织 = 私有链；permissionless 任何人可写入、permissioned 受限节点可写入（"modify"应理解为写入新块；已有记录改了会被发现、改起来代价高，即 tamper-evident 与 tamper-resistant）；公有链无机密性、只有假名性（假名性 ≠ 机密性），联盟/私有链机密性更高但节点身份须已知。
- **平台**：p24 四类应用（资产管理与追踪、代币、加密货币、智能合约业务逻辑）；三类平台（只做加密货币 / 支持智能合约 / 云上 BaaS，Azure 例已于 2021 年停服）；2×2：Bitcoin（无许可、只交易）、Ethereum（无许可、合约）、Chain Core（联盟、只交易）、Hyperledger Fabric（许可、合约）。
- **比特币**：PoW、P2P、BTC；硬编码的是 DNS 种子；可编程性来自 Bitcoin Script（UTXO 是记账模型）；公私钥用于签名而非加密；1 Satoshi $=10^{-8}$ BTC。工作七步：发给邻居 → 邻居检查 → 进交易池 → 矿工组块挖矿 → 广播 → 全节点检查块 → 加入副本。
- **以太坊**：Ether；智能合约；EVM；已于 2022-09-15 转为 PoS（Ethash 停用）；协议名 devp2p。**两类账户**：EOA（私钥控制、能主动发起交易、创建免费）与合约账户（代码控制、无私钥、只能响应交易、部署收费）。课件 p35 把 CA 说成普通用户、把矿工列为账户类型，都是错的。
- **智能合约两类**：确定性（不依赖外部数据或事件）、非确定性（依赖外部数据，经预言机送上链）。确定性的根源：每个节点都执行，结果必须一致。
- **可扩展性三维度**：节点数、交易量、账本存储。账本只增不减，对低存储的无线节点是问题。
- **吞吐量**：三个限制因素（每块交易数、交易速度、出块间隔）↔ 三条对策（每块多装、快速共识、缩短出块间隔）。公式（L15）$\text{Throughput}=\dfrac{\text{Block Size}}{\text{Tx Size}\times\text{Block Time}}$；模拟卷 6 MB、80 B、200 s → **375 Tx/s**（参考答案 37.5 错），20 块确认 = 4000 s。
- **广义链下**（课件 p44、L15 p54 的口径）包括：**侧链**（独立的链，双向锚定与主链互通）与**支付通道**（狭义链下交易：不上链、只在开关通道时上链，如闪电网络）；另有主链只存哈希、数据放链外。
- **分片**：节点分组，每组并行处理一部分交易；挑战：账本副本、分片间通信。**优点**（Q3(b)(v)）：high scalability、greater transaction capacity、low cost。
- **互操作**：多条账本由不同组织为不同目的建造，需要交换信息；八个因素（智能合约、兑换、共识协议、代际、交易速度、语义、手续费、代币）；六种途径（侧链、公证人、预言机、区块链路由器、工业方案、哈希时间锁 HTLC）。
